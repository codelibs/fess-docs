==============================
全公司推广步骤：分阶段检查清单
==============================

前言
====

Fess 试用顺利、决定推广到全公司时，让人犹豫的往往不是功能本身，而是先后顺序。
有些设置如果推迟到后面的阶段，返工代价会很大。
例如，在注册认证信息之后再更改加密密钥，已保存的值将无法解密；事后更改文档的权限，则需要重新爬取。

本文按阶段说明在全公司部署 Fess 15.9 的顺序。
针对每个阶段，列出要设置的内容、要确认的内容，以及判断能否进入下一阶段的指标。
指标使用管理界面 [系统信息] > [搜索日志] 中的分析报告。
本文不讲解各项功能的具体步骤，而是链接到介绍该功能的文章。

组成部分与对应文章
==================

全公司部署涉及的组成部分，以及详细介绍各部分的文章如下。

- Fess 本体：提供搜索界面、管理界面、API 和调度器。整体概况见 :doc:`guide-01`，内存与服务器数量的扩展见 :doc:`guide-14`
- OpenSearch：除文档索引外，还保存爬取配置、用户、作业日志和搜索日志。分离与集群化见 :doc:`guide-14`，快照见 :doc:`guide-10`
- 爬虫等子进程：爬取、建议词生成、缩略图生成和分块处理按作业在独立于 Fess 本体的 JVM 中运行。堆的设置见 :doc:`guide-14`
- 插件：数据存储（``fess-ds-*``）、SSO（``fess-sso-*``）、LLM 与嵌入（``fess-llm-*``）、MCP 和多模态搜索（``fess-webapp-*``）等。请安装与 Fess 相同的次版本（15.9.x），安装和删除后重启 Fess。插件的开发方法见 :doc:`guide-17`
- LLM 与嵌入模型（可选）：AI 搜索模式和语义搜索所用的外部服务，或 Ollama 等服务器。设置见 :doc:`guide-18`、:doc:`guide-19`

不保存在 OpenSearch 中的内容，需要在每台 Fess 服务器上分别管理。
包括 [系统] > [通用] 的设置（``system.properties``）、``fess_config.properties``\ （含加密密钥 ``app.cipher.key``）以及已安装的插件这 3 项。
它们的备份方法见 :doc:`guide-10`，用代码管理的方法见 :doc:`guide-16`。

阶段一览
========

.. list-table::
   :header-rows: 1
   :widths: 22 40 38

   * - 阶段
     - 目的
     - 进入下一阶段的标准
   * - 1. 试用
     - 让少数用户搜索，了解大家在找什么
     - 已将热门查询词和零结果查询词记录下来
   * - 2. 公开第一个信息源
     - 带权限公开第一个信息源，建立运维的基础
     - 已记录用户数和点击率的基准值
   * - 3. SSO 与登录
     - 让用户用公司内部 ID 登录，按组区分显示结果
     - 「按角色和组统计的搜索次数」中出现 IdP 的组
   * - 4. 增加信息源
     - 添加 SaaS、云存储和数据库
     - 因缺少文档而产生的零结果查询词消失
   * - 5. 质量改进循环
     - 从搜索日志中找出有问题的查询词并加以修正
     - 与上一时间段相比，修正过的指标没有变差
   * - 6. 规模扩展与自动化
     - 为文档和用户的增长做准备，使环境可以重现
     - [性能] 选项卡中的响应时间在用户增加后也不比扩展前差
   * - 7. AI 功能
     - 添加 AI 搜索模式、语义搜索和 MCP
     - [AI 聊天] 选项卡中记录了请求，且错误率不高于刚引入时

每个阶段都以前一阶段的设置为前提。
特别是阶段 2 和阶段 3 包含事后更改就需要重新爬取的设置，请不要调换顺序。

阶段 1：试用
============

搭建用于验证的 Fess，让部分部门试用。
这一阶段的目的是以搜索日志的形式收集用户在找什么。

**要设置的内容**

- 按照 :doc:`guide-02` 的步骤，使用 docker-fess 的 ``v15.9.0`` 标签中的 Compose 文件启动，并在首次登录时更改密码
- 将对象限定为一个站点或一个文件夹，创建爬取配置
- 确认 [系统] > [通用] 中的「搜索日志」和「用户日志」已启用（两者默认均为启用）。如果「用户日志」被禁用，将不会统计用户数

**要确认的内容**

- 在 [系统信息] > [作业日志] 中爬取作业变为「OK」，且在 [系统信息] > [爬网信息] 中注册的文档数不为 0
- 如果文档数偏少，查看 [系统信息] > [失败URL]（:doc:`guide-02`）

**进入下一阶段的标准**

- 在 [搜索日志] 的 [概览] 选项卡中，显示试用期间的搜索次数、用户数、热门查询词和零结果查询词
- 点击零结果查询词，在 [日志] 选项卡中确认实际的搜索后，按照 :doc:`guide-08` 中的表格，将原因分为“说法不同”“引导到正式说法”“没有文档”三类
- 归为“没有文档”的查询词，作为阶段 2 和阶段 4 中要添加的信息源的候选。下载表格的 CSV 并保存

阶段 2：公开第一个信息源
========================

选择一个供全公司用户使用的信息源，带权限公开。
同时，建立正式运行所需的监控和备份。

**要设置的内容**

- 在向 Web 认证、文件认证或数据存储的参数中注册认证信息之前，先确定加密密钥 ``app.cipher.key``。注册后再更改，已保存的值将无法解密（:doc:`guide-16`、:doc:`guide-10`）
- 创建网站和共享文件夹的爬取配置、文件认证和标签（:doc:`guide-04`）。如需将文件服务器的 ACL 反映到搜索结果中，参见 :doc:`file-server-search`
- 确定权限的设计（:doc:`guide-05`）。新的爬取配置和标签中带有权限 ``{role}guest``，保持原样的话未登录的用户也能看到。对于按部门区分可见范围的文档，请删除该值后再填写 ``{group}`` 等
- 在 ``{group}`` 中填写的组名，要与阶段 3 中 IdP 传来的名称保持一致。之后再改名，就需要改写权限并重新爬取
- 如果有按每周 1 次等频率由作业运行的爬取配置，请将 [通用] 中的「删除以前的文档」（默认 3 天）设得比爬取间隔更长（:doc:`guide-04`）
- 设置监控、通知和备份（:doc:`guide-10`）。从外部监控工具调用 ``/api/v2/health``，设置 [通用] 中的「通知邮件」或「Slack Webhook URLs」，并通过管理 API 每天获取 [系统信息] > [备份] 中的文件
- 使用 Docker 时，[通用] 的设置保存在 ``fess01`` 容器内的 ``system.properties`` 中，执行 ``down`` 重新创建容器后就会丢失。请将其纳入备份，或通过 ``FESS_JAVA_OPTS`` 传入（:doc:`guide-02`、:doc:`guide-16`）
- 根据需要，在公司门户上放置搜索框（:doc:`guide-03`）

**要确认的内容**

- 用不同部门的用户登录，能看到的文档会发生变化。面向部门的文档所记录的权限中，没有残留初始值 guest 角色（确认方法见 :doc:`guide-05`）
- ``/api/v2/health`` 返回 200，并且用 [通用] 中的 [发送测试邮件] 能收到邮件
- 手动执行一次备份脚本，获取到的文件不为空（:doc:`guide-10`）

**进入下一阶段的标准**

通过 [搜索日志] 无法了解这一阶段的监控和备份状态。
这些请根据上面的“要确认的内容”来判断。
在搜索日志中，获取公开后使用情况的基准值。

- 在 [概览] 选项卡中确认公开后期间的搜索次数、用户数、零结果率和点击率，并以 CSV 保存。之后的阶段中，使用「与上一时间段比较」与这些值进行比较
- [点击] 选项卡的「点击次数最多的 URL」中列出已公开信息源的 URL
- 如果在 [通用] 的「删除以前的搜索日志」中指定了天数，早于该天数的日志将无法用于比较（默认值 ``-1`` 表示不删除）。请事先确定保留期限

阶段 3：SSO 与登录
==================

让用户通过公司内部的身份提供方（IdP）登录，并按 IdP 的组区分显示搜索结果。

这里所说的 SSO，是指 Fess 15.9 中以插件形式提供的 4 种方式。
Entra ID 使用 ``fess-sso-entraid``，OpenID Connect 使用 ``fess-sso-oidc``\ （「SSO Type」为 ``oic``），SAML 使用 ``fess-sso-saml``，SPNEGO 使用 ``fess-sso-spnego``。
Docker 镜像中包含全部 4 个插件，但 ``-slim`` 镜像中不包含。
ZIP、RPM、DEB 版本请通过 [系统] > [插件] 或 ``bin/fess-setup`` 安装。

LDAP 不是 SSO。
[通用] 中的 LDAP 设置，是用 Active Directory 等验证在 Fess 登录界面输入的 ID 和密码，并获取所属组的功能（:doc:`guide-05`）。
SPNEGO 在获取组时使用这一 LDAP 设置。

**要设置的内容**

- 安装插件并重启 Fess，然后在 [通用] 中设置「SSO Type」和 IdP 的信息。在 IdP 中注册的返回地址为 ``https://<Fess主机>/sso/``\ （:doc:`guide-15`）
- 部署在终止 TLS 的反向代理之后时，需要将外部的协议和端口告知 Fess（:doc:`guide-15`）
- 如果不允许未登录的用户搜索，请启用 [通用] 中的「需要登录」

「需要登录」不仅作用于搜索界面。

- ``/api/v2/`` 的搜索 API 对既没有登录会话也没有有效访问令牌的调用返回 401。对于来自业务系统的调用，请准备令牌（:doc:`guide-11`）
- 在 MCP 默认的 ``mcp.auth.mode=none`` 下，``/mcp`` 会以 HTTP 403 拒绝来自 AI 代理的调用。如需使用，请改为通过访问令牌进行认证的设置（:doc:`guide-20`）

**要确认的内容**

- 打开 ``/sso/`` 能通过 IdP 登录，且各部门能看到的文档按阶段 2 的设计发生变化（:doc:`guide-15`）
- 如果用多台服务器运行 Fess，已在负载均衡器上启用粘性会话。15.9 的登录会话保存在各台 Fess 的内存中

**进入下一阶段的标准**

- 在 [搜索日志] 的 [用户与环境] 选项卡的「按角色和组统计的搜索次数」中，以 ``{group}<组名>`` 的形式列出 IdP 传来的组的行
- 如果没有出现组的行，说明要么用户在未登录的状态下搜索（计入 ``{role}guest`` 行），要么组没有传到 Fess
- [概览] 选项卡中的用户数与阶段 2 的基准值相比没有大幅减少。通过「按角色和组统计的搜索次数」中的「用户数」列，确认没有部门因为引入登录而停止使用

阶段 4：增加信息源
==================

通过数据存储插件，添加网站和文件服务器以外的信息源。
所有信息源共通的步骤（插件的安装、参数与脚本、权限、作业、结果的确认方法）汇总在 :doc:`datastore-basics` 中。
请先阅读这篇文章。

**要设置的内容**

- 为每个信息源安装插件并重启

  - Git、Confluence/Jira、Slack：``fess-ds-git``、``fess-ds-atlassian``、``fess-ds-slack``\ （:doc:`guide-06`）
  - Google Drive、SharePoint/OneDrive、Box：``fess-ds-gsuite``、``fess-ds-microsoft365``、``fess-ds-box``\ （:doc:`guide-07`）
  - 数据库、CSV、Salesforce：``fess-ds-db``、``fess-ds-csv``、``fess-ds-salesforce``\ （:doc:`guide-12`）
  - 没有对应插件的信息源，自己开发插件（:doc:`guide-17`）

- 数据存储的配置中也带有 ``{role}guest``。请按每个配置决定是继承信息源的权限，还是用阶段 2 的 ``{group}`` 来填写
- 通过 [创建新作业] 为每个配置单独建立作业，以便按信息源处理 API 的速率限制和认证信息的有效期
- 为每个信息源加上标签，以便在搜索界面中筛选。数据存储的配置中没有标签项，因此通过脚本或标签的「包含的路径」来添加（:doc:`datastore-basics`）

**要确认的内容**

- 数据存储的作业即使连接器中发生错误，也可能以「OK」结束。请结合 [爬网信息] 中的「索引大小 (数据存储)」、[失败URL] 和 ``fess-crawler.log`` 进行确认（:doc:`datastore-basics`）
- 对于继承了权限的信息源，用权限不同的用户搜索时能看到的文档会发生变化

**进入下一阶段的标准**

- 在阶段 1 和阶段 2 中归为“没有文档”的零结果查询词，在添加信息源之后的期间内，从 [查询词] 选项卡的零结果查询词中消失
- [点击] 选项卡的「点击次数最多的 URL」中出现所添加信息源的文档。没有出现的信息源，要么没有被搜索，要么没有排在结果的前列。后者在阶段 5 中处理

阶段 5：质量改进循环
====================

信息源齐备后，定期查看搜索日志，修正有问题的查询词。
修正方法的选择和生效步骤见 :doc:`guide-08`。

**要设置的内容**

- 零结果查询词使用同义词或相关查询，排名靠后的文档使用关键词匹配或文档提升（:doc:`guide-08`）。更改同义词词典后，在 [系统信息] > [维护] 中重新加载文档索引
- 如果日语、英语、中文混杂的文档存在漏检，请检查各语言的字段和词典（:doc:`guide-09`）
- 需要内置报告中没有的统计（按查询词统计打开的 URL、按角色统计的零结果查询词、长期按月的变化趋势等）时，使用 OpenSearch Dashboards（:doc:`guide-22`）
- 如需用代码管理词典和关键词匹配的设置，参见 :doc:`guide-16`

**要确认的内容**

- 在搜索界面中用修正过的查询词搜索，目标文档能被检索到或排在前列
- 关键词匹配的详细界面的「URL」项中显示目标文档（:doc:`guide-08`）

**进入下一阶段的标准**

这一阶段没有终点，需要反复进行。
每次改进的效果按如下方式确认。

- 将期间设为「自定义」，从变更日的次日开始取值，并启用「与上一时间段比较」
- 修正零结果查询词时，查看 [概览] 选项卡的零结果率和 [查询词] 选项卡的零结果查询词；修正排名时，查看 [查询词] 选项卡的平均点击位置和 [点击] 选项卡的点击位置分布
- 如果修正过的查询词从列表中消失，且整体指标不比上一时间段差，就保留该变更

阶段 6：规模扩展与自动化
========================

文档和用户增加后，先确认哪里不足再进行扩展。
同时，使同样的环境可以重新构建。

**要设置的内容**

- 根据症状确认哪里不足（:doc:`guide-14`）。``fess-crawler.log`` 中的 OutOfMemoryError 是爬虫 JVM（``jvm.crawler.options``）的不足，增加 Fess 本体的堆（``FESS_HEAP_SIZE``）也无法解决
- 按照将 OpenSearch 分离到其他服务器、组成 3 台集群、将 Fess 扩展为多台的顺序进行考虑（:doc:`guide-14`）
- 将 Fess 扩展为多台时，把爬取交给其中 1 台。``scheduler.target.name`` 和 [系统] > [调度器] 中的「目标」都要设置（:doc:`guide-14`）
- 多台运行时，让所有服务器上的 ``app.cipher.key``、``fess_config.properties``、[通用] 的设置和插件保持一致
- 固定 Docker 镜像的标签和插件的版本，使设置可以通过 fessctl 和管理 API 应用（:doc:`guide-16`）
- 一个 Fess 由多个组织分别使用时，将虚拟主机与角色结合使用。仅靠虚拟主机无法实现访问控制（:doc:`guide-13`）

**要确认的内容**

- 比较扩展前后 ``/api/admin/stats`` 的堆使用率和 [系统信息] > [作业日志] 中爬取的耗时（:doc:`guide-10`）
- 多台运行时，无论从哪台打开搜索结果都相同，且爬取只在负责的服务器上运行。在其他服务器上点击 [立即开始] 也不会执行（:doc:`guide-14`）
- 能够从备份将设置恢复到重新构建的环境中（:doc:`guide-10`）

**进入下一阶段的标准**

- 在 [搜索日志] 的 [性能] 选项卡中，响应时间的中位数、p95、p99 低于扩展前，或在用户增加后也没有上升
- 用「响应最慢的查询词」中列出的查询词进行搜索，区分是只有特定查询词慢，还是整体都慢

另外，将登录会话保存到 OpenSearch 并在多台之间共享的功能，从 15.10 起才能使用。
在 15.9 中，请使用前面提到的粘性会话来运行。

阶段 7：AI 功能
===============

AI 功能的准备工作因功能而异。
请从符合目的的功能开始添加。

**AI 搜索模式（RAG）**

- 由 LLM 以公司内部文档为依据回答用户提问的功能（:doc:`guide-19`）
- 不需要向量搜索。依据文档通过普通搜索收集，因此阶段 2～3 的权限照样生效，用户无权查看的文档不会用于回答
- 需要 ``fess_config.properties`` 中的 ``rag.chat.enabled=true``\ （默认值为 ``false``，管理界面中没有对应项）、``fess-llm-*`` 插件以及 [通用] 中的「LLM提供商」这 3 项
- 可以通过 [通用] 中的「聊天权限」限制可使用的用户

**语义搜索与多模态搜索**

- 语义搜索即使关键词不一致，也能找到意思相近的文档（:doc:`guide-18`）。通过 ``content_chunker.embedding.name`` 选择嵌入的提供方。默认的 ``opensearch`` 使用 OpenSearch ML Commons 中的模型，``ollama``、``openai``、``gemini``、``bedrock`` 则需要对应的 ``fess-llm-*`` 插件
- 在已有环境中启用时，需要先重新创建索引，再为所有文档生成向量。使用 OpenAI 等按量计费的模型时，首次处理会产生全部文档的费用
- 多模态搜索使用插件 ``fess-webapp-multimodal`` 和 CLIP 服务器，通过文本查找图像（:doc:`guide-21`）
- 这两者无法在同一个 Fess 中同时使用。两者都需要时，请分别构建 Fess

**MCP**

- 让 AI 代理搜索 Fess 的功能（:doc:`guide-20`）。安装插件 ``fess-webapp-mcp`` 后即可使用 ``/mcp``
- 在默认的 ``mcp.auth.mode=none`` 下，任何能访问 ``/mcp`` 的人都可以以访客身份搜索。在公司内部公开之前，请改为通过访问令牌等进行认证的设置

**要确认的内容**

- AI 搜索模式：在搜索界面的 [AI搜索] 中提问，会显示回答和出处。用权限不同的用户确认时，无权查看的文档不会出现在出处中（:doc:`guide-19`）
- 语义搜索与多模态搜索：文档中写入了向量，且搜索 API 的响应中使用了向量搜索（:doc:`guide-18`、:doc:`guide-21`）
- MCP：更改认证设置后，没有令牌的调用会被拒绝（:doc:`guide-20`）

**进入下一阶段的标准**

- AI 搜索模式：在 [搜索日志] 的 [AI 聊天] 选项卡中查看请求数、用户数、错误率和平均响应时间。令牌数仅在 LLM 插件报告时才会记录，提问和回答的内容不会被记录
- 语义搜索：以引入日次日起的期间启用「与上一时间段比较」，比较零结果率、点击率和 [性能] 选项卡中的响应时间
- MCP 和多模态搜索在 [搜索日志] 中没有专用的指标。请根据上面的“要确认的内容”和使用部门的反馈来判断
