================================
用开源方案实现文件服务器全文检索
================================

前言
====

随着各部门的文件服务器不断增加，“那份资料到底在哪里”就变得谁也说不清了。
Windows 搜索只能在单个共享文件夹内工作，服务器一多就无法跨服务器搜索。
NAS 自带的全文搜索功能也无法跨设备使用。

解决这一问题的方法之一，是搭建一台专门面向文件服务器的全文搜索服务器。
本页总结了在使用开源全文搜索服务器 Fess 搜索文件服务器时，导入前需要确认的要点。
内容基于 Fess 15.9。

目标读者
========

- 苦于无法有效搜索公司内部文件服务器或 NAS 的读者
- 正在考虑导入全文搜索，想了解能否用开源方案实现的读者
- 希望在不破坏现有访问权限的前提下导入搜索的读者

Fess 以 Apache License 2.0 发布，无需支付许可费用即可使用。

可以搜索存放在哪里的文件
========================

Fess 的文件爬取支持以下协议。
在管理界面的 [爬虫] > [文件系统] 中进行设置，在「路径」中指定开始爬取的位置。

.. list-table:: 支持的协议
   :header-rows: 1
   :widths: 12 33 55

   * - 协议
     - 路径格式
     - 主要用途
   * - ``file``
     - ``file:/home/share/documents/``
     - 运行 Fess 的服务器上的目录。已挂载的 NAS 也包括在内
   * - ``smb``
     - ``smb://fileserver.example.com/share/``
     - Windows 文件共享，以及通过 SMB 共享文件的 NAS
   * - ``smb1``
     - ``smb1://fileserver.example.com/share/``
     - 使用旧版 SMB1 实现的连接。旧设备无法用 ``smb`` 连接时的备用方案
   * - ``ftp``
     - ``ftp://fileserver.example.com/pub/``
     - FTP 服务器
   * - ``s3``
     - ``s3://bucket-name/prefix/``
     - Amazon S3 及兼容 S3 的对象存储（需要 ``fess-storage-s3`` 插件）
   * - ``gcs``
     - ``gcs://bucket-name/prefix/``
     - Google Cloud Storage（需要 ``fess-storage-gcs`` 插件）

Fess 本体处理的协议由配置项 ``crawler.file.protocols`` 决定，15.9 的默认值为 ``file,smb,smb1,ftp``。
``s3`` 和 ``gcs`` 在 15.9 中已从本体拆分为插件。
Docker 镜像中已包含这两个插件，但对于通过 ZIP 或 RPM/DEB 安装的 Fess，需要在 [系统] > [插件] 中安装，并重启 Fess 后才能使用。

搜索 Windows 文件共享时请使用 ``smb``。
如果不在 Fess 端做特别设置，``smb`` 会在 SMB1 到 SMB 3.1.1 的范围内与服务器协商连接版本。
``smb1`` 用于通过另一种实现（旧版 jcifs）进行连接，不应在新部署中选用。

沿用现有的访问权限
==================

为文件服务器导入搜索时，最大的顾虑是“不应看到的文档出现在搜索结果中”。
如果人事或财务的共享文件夹出现在全体员工的搜索结果里，搜索系统本身就无法使用了。

Fess 通过把文件服务器端的访问权限带入搜索来解决这个问题。
不过，新建的爬取配置如果保持原样，并不会按权限区分显示结果。请务必确认下面的机制，以及接下来的“删除权限栏中的 {role}guest”一节。

工作机制
--------

1. 爬取时，Fess 读取每个文件的 ACL（访问控制列表）
2. 将允许读取的账户和组、被拒绝的账户和组，作为该文档的“角色”记录到 ``role`` 字段中
3. 爬取配置的「权限」栏中填写的值也会追加到同一个 ``role`` 字段中
4. 搜索时，将其与已登录用户所拥有的角色进行比对，只返回有权限的文档

在 ``role`` 字段中，用户以名称前加 ``1``、组以名称前加 ``2`` 的形式记录（例如 ``1taro``、``2sales``）。
拒绝条目还会在最前面加上 ``D``\ （例如 ``D2contractors``）。
在权限栏中写作 ``{role}guest`` 的值会记录为 ``Rguest``。
管理界面中看到的 ``(allow)`` 和 ``(deny)`` 是在权限栏中输入时的写法，并不是被记录的值。

从 ACL 提取角色的功能默认启用。

.. list-table:: 与沿用权限相关的配置项（fess_config.properties）
   :header-rows: 1
   :widths: 38 14 48

   * - 配置项
     - 默认值
     - 说明
   * - ``smb.role.from.file``
     - ``true``
     - 从通过 ``smb`` 和 ``smb1`` 爬取的文件的 ACL 中获取角色
   * - ``file.role.from.file``
     - ``true``
     - 从通过 ``file`` 爬取的文件的访问权限中获取角色（参见后文的注意事项）
   * - ``ftp.role.from.file``
     - ``true``
     - 从通过 ``ftp`` 爬取的文件的所有者和组中获取角色
   * - ``smb.available.sid.types``
     - ``1,2,4:2,5:1``
     - 作为角色采用的 SID 类型，以及记录时使用的类型。默认情况下，用户（1）和域组（2）按原样记录，本地组（4）记录为组，Everyone 等内置 SID（5）记录为用户

删除权限栏中的 {role}guest
--------------------------

在 [爬虫] > [文件系统] 中新建配置时，「权限」栏中已预先填入 ``{role}guest``。
如果直接保存，所有文档除了来自 ACL 的角色之外，还会带上 ``Rguest``。
由于未登录的用户会被赋予 ``guest`` 角色，\ **即使是用 ACL 限制过的文件，在未登录状态下搜索时也会全部显示**\ 。

要让基于 ACL 的区分显示生效，请从爬取配置的「权限」栏中删除 ``{role}guest`` 并保存。
即使已经爬取过，下次爬取时文档也会以新的权限重新登记。

另外，已登录的用户不会被赋予 ``guest`` 角色。
因此即使保留了 ``{role}guest``，已登录用户得到的也是符合 ACL 的结果。
请按照“确认运行效果”中的说明，务必在未登录状态下也进行确认。

与登录端的名称保持一致
----------------------

要让这一机制完整地发挥作用，搜索端的用户也必须拥有相同的角色。
文档端记录的是“这个组的成员可以读取”，因此如果搜索的用户无法把自己所属的组告诉 Fess，就无法进行比对。

所以，要实现沿用权限的搜索，前提是与 Active Directory 或 LDAP 集成。
也就是让 Fess 的登录使用与文件服务器认证相同的目录服务。
LDAP 在 [系统] > [通用] 中设置。
具体步骤和角色的设计思路在 :doc:`guide-05` 中说明。

由于比对是基于名称字符串进行的，请注意以下几点。

- 从 ACL 获取的名称以不含域名的账户名记录（``EXAMPLE\taro`` 记录为 ``1taro``）
- 通过 LDAP 登录的用户，其组名默认取自 ``memberOf`` 中的 CN。如果文件服务器端组的账户名与 CN 不同，就无法匹配
- Everyone 等内置组会记录为同名的角色。通过 LDAP 登录的用户通常不具备这些角色，因此只对内置组公开的文件夹可能对任何人都不显示。必要时请拆分爬取配置，并在权限栏中补充角色

反过来，如果只把全体员工可以看到相同范围的共享文件夹作为对象，则不一定需要这种集成。
这正是确定导入范围时的分水岭。

各协议的注意事项
----------------

``smb`` / ``smb1``
   爬取用账户除了需要能读取文件内容，还需要有读取文件访问权限（安全信息）的权限。
   无法读取访问权限的文件不会被索引，并会记录在 [系统信息] > [失败URL] 中。

``file``
   如果文件系统不提供 ACL（如常见的 Linux 文件系统），则只记录所有者用户和组这两个角色。
   即使对“其他人”允许了读取，也不会成为角色。
   如果把 NAS 挂载到 Fess 服务器上并用 ``file`` 爬取，记录的是在挂载点上看到的所有者，而不是 NAS 端的 ACL。
   需要按 ACL 区分显示的文件服务器，请不要挂载，而是直接用 ``smb`` 爬取。

``ftp``
   将 FTP 服务器返回的所有者和组记录为角色。

能读取哪些文件格式的内容
========================

Fess 利用 Apache Tika 从文件内容中提取文本。
由于不仅是文件名，正文也会成为搜索对象，因此即使是“想不起标题的资料”也能找到。

主要支持的格式如下。

- MS Office（doc、xls、ppt、docx、xlsx、pptx 等）
- PDF
- 文本、HTML、XML
- 富文本（rtf）
- 源代码（js、c、h、java 等）
- 压缩文件（gz、tar、zip 等）

完整列表请参阅 `搜索对象文件 <https://fess.codelibs.org/zh-cn/supported-files.html>`__。

图片 PDF 或扫描文档这类不含文本的文件，直接是无法搜索正文的。
在 Fess 15.9 中可以启用基于 Tesseract 的 OCR，从图片文件、Office 文档中嵌入的图片以及不含文本的 PDF 中识别文字。
OCR 默认处于禁用状态。
在运行爬虫的主机上安装 ``tesseract``，并设置 ``crawler.document.ocr.enabled=true``。
只有部分页面是扫描图片的 PDF 不在处理范围内。
具体步骤请参阅 `OCR（图像文字识别）配置 <https://fess.codelibs.org/zh-cn/stable/config/crawler-ocr.html>`__。
使用 OCR 会延长爬取时间，建议先确认目标文件夹中有多少扫描文档。

架构与规模
==========

Fess 使用 OpenSearch 存储搜索索引。
规模较小时，可以让 Fess 和 OpenSearch 共存于同一台服务器上运行；目标文件增多后，可以把 OpenSearch 分离为集群架构。

估算规模时，除了文件数之外，再确认以下几点可以提高准确度。

- 目标文件夹的总大小，以及其中包含文本的文件所占比例
- 更新频率（每天都变，还是每月几次）。这会影响爬取执行间隔的设计
- 每个文件的大小

可索引的文件大小默认有上限。
``app/WEB-INF/classes/crawler/contentlength.xml`` 的默认值为 HTML 2.5MB、其他文件 10MB，超过该值的文件不会被索引，并记录在 [失败URL] 中。
此外，在爬取配置的「配置参数」中写入 ``client.maxContentLength=10485760`` 这样的内容，可以限制所获取文件本身的大小（默认不限制）。
对于大文件较多的文件夹，请在导入前决定是否调整这些上限。
设置方法请参阅 `爬虫配置 <https://fess.codelibs.org/zh-cn/stable/config/crawler-basic.html>`__ 中关于文件大小设置的小节。

爬取的执行间隔也需要注意。
Fess 会把在一定天数内没有被爬取更新的文档从索引中删除。
这个天数就是 [系统] > [通用] 中的「删除以前的文档」，默认为 3 天。
默认作业“Default Crawler”每天执行，因此没有问题；但如果减少到每周一次等，请把这个天数设置得比执行间隔更长。

选择文件服务器搜索工具的要点
============================

比较面向文件服务器的搜索工具时，与其先比较产品名称，不如先确认是否满足以下几点，这样更容易做出选择。

.. list-table:: 选择搜索工具时的确认项目
   :header-rows: 1
   :widths: 30 70

   * - 确认项目
     - Fess 的情况
   * - 能否跨多台服务器或 NAS 搜索
     - 通过登记多个爬取配置，可以在一个搜索框中跨范围搜索
   * - 能否搜索到文件正文
     - 通过 Apache Tika 提取 Office 文档和 PDF 的正文作为搜索对象。启用 OCR 后，扫描文档也会成为搜索对象
   * - 能否沿用现有的访问权限
     - 从通过 SMB 爬取的文件的 ACL 中获取角色，并据此区分显示搜索结果。需要与 Active Directory 或 LDAP 集成，并重新检查爬取配置中的权限栏
   * - 是否需要许可费用
     - 以 Apache License 2.0 发布，无需许可费用
   * - 能否在本地试用
     - 可以用 Docker Compose 启动，在本地试用搜索

导入流程
========

1. **先运行起来** — 按照 `快速构建指南 <https://fess.codelibs.org/zh-cn/quick-start.html>`__ 或 :doc:`guide-02` 中的步骤启动 Fess
2. **创建爬取配置** — 在 [爬虫] > [文件系统] 中登记名称和路径。如果要按 ACL 区分显示，请先删除「权限」栏中的 ``{role}guest`` 再保存
3. **设置认证信息** — 在 [爬虫] > [文件认证] 中登记用于访问共享文件夹的账户，并在「文件爬网配置」中选择第 2 步的配置
4. **确认爬取用账户的权限** — 在文件服务器端确认该账户能否读取目标文件夹的内容和访问权限
5. **集成登录** — 在 [系统] > [通用] 中设置 LDAP（Active Directory）
6. **执行爬取并确认** — 在 [系统] > [调度器] 中打开“Default Crawler”，点击 [立即开始]，然后按照下面的“确认运行效果”确认结果

如果需要按部门筛选，还要在 [爬虫] > [标签] 中设置标签。

让多台文件服务器和公司内部网站可以从一个搜索框中查找的具体步骤见 :doc:`guide-04`，基于角色和组区分显示结果的设计见 :doc:`guide-05`。

确认运行效果
============

爬取完成后，按以下顺序进行确认。
内置的 ``admin`` 用户也拥有 ``guest`` 角色，因此请不要用它来确认区分显示。

1. 打开 [系统信息] > [失败URL]，确认没有因访问错误或超出大小限制而未能导入的文件
2. 在 [系统信息] > [搜索] 中搜索受限文件夹中的文件。该界面不按角色筛选，因此会显示所有文档
3. 点击结果的 [更新] 打开编辑界面，确认 ``role`` 栏。确认其中包含 ``1taro`` 或 ``2sales`` 这样来自 ACL 的值，并且不包含 ``Rguest``
4. 在已注销的状态下，从搜索页面搜索同一文件，确认不会显示
5. 以属于能读取该文件夹的组的用户登录并搜索，确认会显示
6. 以不属于该组的用户登录并搜索，确认不会显示

如果第 3 步中 ``role`` 栏里的名称与 LDAP 端的名称不一致，请重新检查“与登录端的名称保持一致”中的各项。

总结
====

- Fess 是一款可以把文件服务器（SMB、FTP、本地）作为全文检索对象的开源搜索服务器。S3 和 GCS 通过插件支持
- 对于通过 SMB 爬取的文件，ACL 中记录的访问权限会用于区分显示搜索结果。ACL 的读取默认启用
- 如果不删除爬取配置「权限」栏中的 ``{role}guest``，未登录的用户将看到全部文档
- 要实现沿用权限的搜索，前提是与 Active Directory 或 LDAP 集成，并且两端的名称一致
- 借助 Apache Tika，Office 文档和 PDF 的正文也能成为搜索对象；启用 OCR 后，扫描文档也能成为搜索对象
- 可以从小规模起步，在对象增多后通过将 OpenSearch 集群化来扩展
