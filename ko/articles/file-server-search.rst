=======================================
오픈소스로 구현하는 파일 서버 전문 검색
=======================================

들어가며
========

부서마다 파일 서버가 늘어나면 "그 자료가 어디에 있는지" 아무도 알 수 없게 됩니다.
Windows 검색은 공유 폴더 단위로만 동작하므로 서버가 여러 대이면 가로질러 검색할 수 없습니다.
NAS의 전문 검색 기능도 장비를 넘나들며 사용할 수는 없습니다.

이 문제를 해결하는 방법 중 하나는 파일 서버 전용 전문 검색 서버를 구축하는 것입니다.
이 페이지에서는 오픈소스 전문 검색 서버 Fess로 파일 서버를 검색 대상으로 삼을 때 도입 전에 확인해 두어야 할 점을 정리합니다.
내용은 Fess 15.9를 기준으로 합니다.

대상 독자
=========

- 사내 파일 서버나 NAS 검색에 어려움을 겪고 있는 분
- 전문 검색 도입을 검토 중이며 오픈소스로 구현할 수 있는지 알고 싶은 분
- 기존 접근 권한을 깨뜨리지 않고 검색을 도입하고 싶은 분

Fess는 Apache License 2.0으로 공개되어 있어 라이선스 비용 없이 이용할 수 있습니다.

어디에 있는 파일을 검색할 수 있는가
===================================

Fess의 파일 크롤링은 다음 프로토콜을 지원합니다.
설정은 관리 화면의 [크롤러] > [파일 시스템]에서 하며, "경로"에 크롤링을 시작할 위치를 지정합니다.

.. list-table:: 지원 프로토콜
   :header-rows: 1
   :widths: 12 33 55

   * - 프로토콜
     - 경로 형식
     - 주요 용도
   * - ``file``
     - ``file:/home/share/documents/``
     - Fess를 실행하는 서버의 디렉터리. 마운트한 NAS도 여기에 포함됩니다
   * - ``smb``
     - ``smb://fileserver.example.com/share/``
     - Windows 파일 공유나 SMB로 공개하고 있는 NAS
   * - ``smb1``
     - ``smb1://fileserver.example.com/share/``
     - 기존 SMB1 구현을 사용하는 연결. 오래된 장비에서 ``smb``\ 로 연결되지 않을 때의 예비 수단
   * - ``ftp``
     - ``ftp://fileserver.example.com/pub/``
     - FTP 서버
   * - ``s3``
     - ``s3://bucket-name/prefix/``
     - Amazon S3 및 S3 호환 오브젝트 스토리지(\ ``fess-storage-s3`` 플러그인 필요)
   * - ``gcs``
     - ``gcs://bucket-name/prefix/``
     - Google Cloud Storage(\ ``fess-storage-gcs`` 플러그인 필요)

Fess 본체가 다루는 프로토콜은 설정값 ``crawler.file.protocols``\ 로 정해지며, 15.9의 기본값은 ``file,smb,smb1,ftp``\ 입니다.
``s3``\ 와 ``gcs``\ 는 15.9에서 본체로부터 플러그인으로 분리되었습니다.
Docker 이미지에는 두 플러그인이 함께 포함되어 있지만, ZIP이나 RPM/DEB로 설치한 Fess에서는 [시스템] > [플러그인]에서 설치하고 Fess를 재시작한 뒤에 사용합니다.

Windows 파일 공유를 검색할 때는 ``smb``\ 를 사용합니다.
``smb``\ 는 Fess 측에서 따로 설정하지 않으면 SMB1부터 SMB 3.1.1까지의 범위에서 서버와 연결 버전을 결정합니다.
``smb1``\ 은 다른 구현(기존 jcifs)으로 연결하기 위한 지정이며, 새로 선택할 대상은 아닙니다.

기존 접근 권한을 그대로 이어받기
================================

파일 서버에 검색을 도입할 때 가장 큰 우려는 "보여서는 안 되는 문서가 검색 결과에 나오는 것"입니다.
인사나 경리의 공유 폴더가 전 직원의 검색 결과에 나열된다면 검색 시스템 자체를 쓸 수 없습니다.

Fess는 파일 서버 측의 접근 권한을 검색에 가져오는 방법으로 이를 해결합니다.
다만 새로 만든 크롤링 설정 그대로는 권한에 따른 구분 표시가 적용되지 않습니다. 다음 구조와 이어지는 "권한 항목의 {role}guest 지우기"를 반드시 확인하십시오.

구조
----

1. 크롤링 시 Fess는 각 파일의 ACL(접근 제어 목록)을 읽습니다
2. 읽기가 허용된 계정과 그룹, 거부된 계정과 그룹을 그 문서의 "역할"로서 ``role`` 필드에 기록합니다
3. 크롤링 설정의 "권한" 항목에 적은 값도 같은 ``role`` 필드에 추가됩니다
4. 검색 시 로그인한 사용자가 가진 역할과 대조하여 권한이 있는 문서만 반환합니다

``role`` 필드에는 사용자는 ``1``, 그룹은 ``2``\ 를 이름 앞에 붙인 형태로 기록됩니다(예: ``1taro``, ``2sales``\ ).
거부 항목에는 앞에 ``D``\ 가 더 붙습니다(예: ``D2contractors``\ ).
권한 항목에 ``{role}guest``\ 로 적은 값은 ``Rguest``\ 로 기록됩니다.
관리 화면에서 볼 수 있는 ``(allow)``\ 와 ``(deny)``\ 는 권한 항목에 입력할 때의 표기법이며, 기록되는 값이 아닙니다.

ACL에서 역할을 추출하는 동작은 기본으로 활성화되어 있습니다.

.. list-table:: 권한 이어받기에 관한 설정값(fess_config.properties)
   :header-rows: 1
   :widths: 38 14 48

   * - 설정값
     - 기본값
     - 내용
   * - ``smb.role.from.file``
     - ``true``
     - ``smb``\ 와 ``smb1``\ 로 크롤링한 파일의 ACL에서 역할을 가져옵니다
   * - ``file.role.from.file``
     - ``true``
     - ``file``\ 로 크롤링한 파일의 접근 권한에서 역할을 가져옵니다(뒤의 주의 사항 참조)
   * - ``ftp.role.from.file``
     - ``true``
     - ``ftp``\ 로 크롤링한 파일의 소유자와 그룹에서 역할을 가져옵니다
   * - ``smb.available.sid.types``
     - ``1,2,4:2,5:1``
     - 역할로 채택할 SID의 종류와 기록할 때의 종류. 기본적으로 사용자(1)와 도메인 그룹(2)은 그대로, 로컬 그룹(4)은 그룹으로, Everyone 등의 기본 제공 SID(5)는 사용자로 기록합니다

권한 항목의 {role}guest 지우기
------------------------------

[크롤러] > [파일 시스템]에서 새로 만들면 "권한" 항목에는 미리 ``{role}guest``\ 가 들어 있습니다.
이대로 저장하면 모든 문서에 ACL에서 유래한 역할과 함께 ``Rguest``\ 가 붙습니다.
로그인하지 않은 이용자에게는 ``guest`` 역할이 부여되므로, \ **ACL로 제한한 파일도 로그인하지 않은 검색에서는 모두 표시됩니다**\ .

ACL에 따른 구분 표시를 적용하려면 크롤링 설정의 "권한" 항목에서 ``{role}guest``\ 를 삭제하고 저장합니다.
이미 크롤링한 경우에도 다음 크롤링 때 새 권한의 문서로 다시 등록됩니다.

참고로 로그인한 사용자에게는 ``guest`` 역할이 부여되지 않습니다.
따라서 ``{role}guest``\ 를 남겨 두어도 로그인한 사용자에게는 ACL대로의 결과가 반환됩니다.
"동작 확인하기"에서 설명하듯이 반드시 로그인하지 않은 상태에서도 확인하십시오.

로그인 측의 이름과 일치시키기
-----------------------------

이 구조가 끝까지 동작하려면 검색하는 쪽의 사용자에게도 같은 역할이 붙어 있어야 합니다.
문서 측에는 "이 그룹이라면 읽을 수 있다"고 기록되어 있으므로, 검색하는 사용자가 자신이 속한 그룹을 Fess에 전달할 수 없으면 대조할 수 없습니다.

따라서 권한을 이어받은 검색을 하려면 Active Directory나 LDAP과의 연동이 전제가 됩니다.
파일 서버 인증에 사용하는 디렉터리와 같은 것을 Fess 로그인에도 사용하는 구성입니다.
LDAP 설정은 [시스템] > [일반]에서 합니다.
절차와 역할에 대한 사고방식은 :doc:`guide-05`\ 에서 설명합니다.

대조는 이름 문자열로 이루어지므로 다음 사항에 주의하십시오.

- ACL에서 가져온 이름은 도메인 이름을 포함하지 않는 계정 이름으로 기록됩니다(\ ``EXAMPLE\taro``\ 라면 ``1taro``\ )
- LDAP으로 로그인한 사용자의 그룹 이름은 기본적으로 ``memberOf``\ 의 CN에서 가져옵니다. 파일 서버 측 그룹의 계정 이름과 CN이 다르면 일치하지 않습니다
- Everyone 등의 기본 제공 그룹은 그 이름의 역할로 기록됩니다. LDAP으로 로그인한 사용자에게는 보통 그 역할이 붙지 않으므로, 기본 제공 그룹에만 공개한 폴더는 아무에게도 표시되지 않을 수 있습니다. 필요에 따라 크롤링 설정을 나누고 권한 항목에서 역할을 보완하십시오

반대로 전 직원이 같은 범위를 봐도 되는 공유 폴더만 대상으로 한다면 이 연동은 필수가 아닙니다.
이 점이 도입 범위를 정할 때의 갈림길이 됩니다.

프로토콜별 주의 사항
--------------------

``smb`` / ``smb1``
   크롤링용 계정에는 파일 내용에 더해 파일의 접근 권한(보안 정보)을 읽을 수 있는 권한이 필요합니다.
   접근 권한을 읽지 못한 파일은 인덱싱되지 않고 [시스템 정보] > [장애 URL]에 기록됩니다.

``file``
   파일 시스템이 ACL을 제공하지 않는 경우(일반적인 Linux 파일 시스템 등)에는 소유자인 사용자와 그룹 두 가지만 역할로 기록합니다.
   "기타"에 읽기를 허용하더라도 그것은 역할이 되지 않습니다.
   NAS를 Fess 서버에 마운트하여 ``file``\ 로 크롤링하면 NAS 측의 ACL이 아니라 마운트 지점에서 보이는 소유자가 기록됩니다.
   ACL로 구분 표시하고 싶은 파일 서버는 마운트하지 말고 ``smb``\ 로 직접 크롤링하십시오.

``ftp``
   FTP 서버가 반환하는 소유자와 그룹을 역할로 기록합니다.

어떤 파일 형식의 내용까지 읽을 수 있는가
========================================

Fess는 Apache Tika를 이용하여 파일 내용에서 텍스트를 추출합니다.
파일 이름뿐 아니라 본문이 검색 대상이 되므로 "제목이 기억나지 않는 자료"도 찾을 수 있습니다.

주요 지원 형식은 다음과 같습니다.

- MS Office(doc, xls, ppt, docx, xlsx, pptx 등)
- PDF
- 텍스트, HTML, XML
- 서식 있는 텍스트(rtf)
- 소스 코드(js, c, h, java 등)
- 압축 파일(gz, tar, zip 등)

전체 목록은 `검색 대상 파일 <https://fess.codelibs.org/ko/supported-files.html>`__\ 을 참조하십시오.

이미지 PDF나 스캔 문서처럼 텍스트를 포함하지 않는 파일은 그대로는 본문을 검색할 수 없습니다.
Fess 15.9에서는 Tesseract를 이용한 OCR을 활성화할 수 있으며, 이미지 파일, Office 문서에 포함된 이미지, 텍스트를 포함하지 않는 PDF에서 문자를 읽어 낼 수 있습니다.
OCR은 기본적으로 비활성화되어 있습니다.
크롤러가 동작하는 호스트에 ``tesseract``\ 를 설치하고 ``crawler.document.ocr.enabled=true``\ 를 설정합니다.
일부 페이지만 스캔 이미지인 PDF는 대상이 아닙니다.
절차는 `OCR(이미지 내 문자 인식) 설정 <https://fess.codelibs.org/ko/stable/config/crawler-ocr.html>`__\ 을 참조하십시오.
OCR을 사용하면 크롤링 시간이 길어지므로, 대상 폴더에 스캔 문서가 얼마나 있는지 먼저 확인해 둘 것을 권장합니다.

구성과 규모
===========

Fess는 검색 인덱스 저장에 OpenSearch를 사용합니다.
소규모라면 Fess와 OpenSearch를 같은 서버에 함께 두는 구성으로 동작하지만, 대상 파일이 늘어나면 OpenSearch를 클러스터 구성으로 분리할 수 있습니다.

규모를 산정할 때는 파일 수뿐 아니라 다음 사항을 확인해 두면 정확도가 높아집니다.

- 대상 폴더의 합계 크기와 그중 텍스트를 포함하는 파일의 비율
- 갱신 빈도(매일 바뀌는지, 한 달에 몇 번인지). 크롤링 실행 간격 설계에 영향을 줍니다
- 파일 1개당 크기

인덱싱할 수 있는 파일 크기에는 기본적으로 상한이 있습니다.
``app/WEB-INF/classes/crawler/contentlength.xml``\ 의 기본값은 HTML이 2.5MB, 그 밖의 파일이 10MB이며, 이를 넘는 파일은 인덱싱되지 않고 [장애 URL]에 기록됩니다.
이와 별도로 크롤링 설정의 "설정 파라미터"에 ``client.maxContentLength=10485760``\ 처럼 적으면 가져오는 파일의 크기 자체를 제한할 수 있습니다(기본값은 제한 없음).
큰 자료가 많은 폴더에서는 상한을 조정할지 여부를 도입 전에 정해 둡니다.
설정 방법은 `크롤러 설정 <https://fess.codelibs.org/ko/stable/config/crawler-basic.html>`__\ 의 파일 크기 설정에 관한 절을 참조하십시오.

크롤링 실행 간격에도 주의가 필요합니다.
Fess는 일정 일수 동안 크롤링으로 갱신되지 않은 문서를 인덱스에서 삭제합니다.
이 일수는 [시스템] > [일반]의 "이전 문서 삭제"이며, 기본값은 3일입니다.
기본 작업 "Default Crawler"는 매일 실행되므로 문제가 없지만, 주 1회 등으로 줄이는 경우에는 이 일수를 실행 간격보다 길게 설정하십시오.

파일 서버 검색 도구를 고르는 관점
=================================

파일 서버용 검색 도구를 비교할 때는 제품 이름을 비교하기 전에 다음 사항을 충족하는지 확인하면 고르기 쉬워집니다.

.. list-table:: 검색 도구를 고를 때의 확인 항목
   :header-rows: 1
   :widths: 30 70

   * - 확인 항목
     - Fess의 경우
   * - 여러 서버나 NAS를 가로질러 검색할 수 있는가
     - 크롤링 설정을 여러 개 등록하면 하나의 검색창에서 가로질러 검색할 수 있습니다
   * - 파일 본문까지 검색할 수 있는가
     - Apache Tika로 Office 문서나 PDF의 본문을 추출하여 검색 대상으로 삼습니다. 스캔 문서는 OCR을 활성화하면 대상이 됩니다
   * - 기존 접근 권한을 이어받을 수 있는가
     - SMB로 크롤링한 파일의 ACL에서 역할을 가져와 검색 결과를 구분하여 표시합니다. Active Directory나 LDAP과의 연동과 크롤링 설정의 권한 항목 재검토가 필요합니다
   * - 라이선스 비용이 드는가
     - Apache License 2.0으로 공개되어 있어 라이선스 비용이 들지 않습니다
   * - 직접 시험해 볼 수 있는가
     - Docker Compose로 실행하여 직접 검색을 시험해 볼 수 있습니다

도입 흐름
=========

1. **먼저 실행해 보기** — `빠른 구축 가이드 <https://fess.codelibs.org/ko/quick-start.html>`__ 또는 :doc:`guide-02`\ 의 절차로 Fess를 실행합니다
2. **크롤링 설정 만들기** — [크롤러] > [파일 시스템]에서 이름과 경로를 등록합니다. ACL로 구분 표시하는 경우에는 "권한" 항목의 ``{role}guest``\ 를 삭제한 뒤 저장합니다
3. **인증 정보 설정하기** — 공유 폴더에 접근하기 위한 계정을 [크롤러] > [파일 인증]에 등록하고, "파일 크롤링 설정"에서 2의 설정을 선택합니다
4. **크롤링용 계정의 권한 확인하기** — 대상 폴더의 내용과 접근 권한을 읽을 수 있는 계정인지 파일 서버 측에서 확인합니다
5. **로그인 연동하기** — [시스템] > [일반]에서 LDAP(Active Directory)를 설정합니다
6. **크롤링을 실행하여 확인하기** — [시스템] > [스케줄러]에서 "Default Crawler"를 열고 [지금 시작]을 클릭한 뒤, 이어지는 "동작 확인하기"에서 결과를 확인합니다

부서별 필터링이 필요하다면 [크롤러] > [라벨]에서 라벨도 설정합니다.

여러 파일 서버와 사내 웹 사이트를 하나의 검색창에서 찾을 수 있게 하는 구체적인 절차는 :doc:`guide-04`\ 에서, 역할과 그룹에 따른 구분 표시 설계는 :doc:`guide-05`\ 에서 다룹니다.

동작 확인하기
=============

크롤링이 끝나면 다음 순서로 확인합니다.
기본 제공 ``admin`` 사용자는 ``guest`` 역할도 가지고 있으므로 구분 표시 확인에는 사용하지 마십시오.

1. [시스템 정보] > [장애 URL]을 열고 접근 오류나 크기 초과로 가져오지 못한 파일이 없는지 확인합니다
2. [시스템 정보] > [검색]에서 제한된 폴더의 파일을 검색합니다. 이 화면에서는 역할에 따른 필터링이 적용되지 않으므로 모든 문서가 표시됩니다
3. 결과의 [갱신]을 클릭하여 편집 화면을 열고 ``role`` 항목을 확인합니다. ``1taro``\ 나 ``2sales``\ 와 같은 ACL 유래의 값이 들어 있는지, ``Rguest``\ 가 들어 있지 않은지 확인합니다
4. 로그아웃한 상태로 검색 화면에서 같은 파일을 검색하여 표시되지 않는지 확인합니다
5. 그 폴더를 읽을 수 있는 그룹에 속한 사용자로 로그인하여 검색하고, 표시되는지 확인합니다
6. 그 그룹에 속하지 않은 사용자로 로그인하여 검색하고, 표시되지 않는지 확인합니다

3에서 ``role`` 항목의 이름이 LDAP 측의 이름과 어긋나는 경우에는 "로그인 측의 이름과 일치시키기"의 각 항목을 재검토합니다.

정리
====

- Fess는 파일 서버(SMB, FTP, 로컬)를 전문 검색 대상으로 삼을 수 있는 오픈소스 검색 서버입니다. S3와 GCS는 플러그인으로 지원합니다
- SMB로 크롤링한 파일은 ACL에 기록된 접근 권한이 검색 결과의 구분 표시에 사용됩니다. ACL 읽기는 기본으로 활성화되어 있습니다
- 크롤링 설정의 "권한" 항목에 있는 ``{role}guest``\ 를 지우지 않으면 로그인하지 않은 이용자에게 모든 문서가 표시됩니다
- 권한을 이어받은 검색을 하려면 Active Directory나 LDAP과의 연동, 그리고 양쪽 이름의 일치가 전제가 됩니다
- Apache Tika로 Office 문서나 PDF의 본문까지 검색 대상이 되며, OCR을 활성화하면 스캔 문서도 대상이 됩니다
- 작게 시작하여 대상이 늘어나면 OpenSearch를 클러스터화하여 확장할 수 있습니다
