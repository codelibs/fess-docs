=========================================
웹 사이트와 파일 서버를 한꺼번에 검색하기
=========================================

들어가며
========

사내 자료는 포털 사이트, 부서별 공유 폴더, 오래된 자료를 모아 둔 아카이브용 디렉터리 등 여러 곳에 흩어져 있기 쉽습니다.
찾는 사람은 자료가 어디에 있는지 먼저 떠올린 다음, 각 위치에서 따로따로 찾아야 합니다.

이 글에서는 Fess 15.9로 다음 3곳을 크롤링하여 하나의 검색창에서 찾을 수 있게 합니다.
검색 화면에서는 라벨을 사용해 "포털만", "공유 폴더만"처럼 범위를 좁힐 수 있게 합니다.

- 사내 포털(웹 사이트)
- Windows 파일 서버의 공유 폴더(SMB)
- 서버의 아카이브용 디렉터리(로컬 파일)

절차는 :doc:`guide-02`\ 에서 기동한 Docker 환경(``fess01``\ 과 ``search01``)을 전제로 합니다.
Google Drive, SharePoint, Box 등의 클라우드 스토리지는 :doc:`guide-07`\ 에서 다룹니다.
파일 서버 검색을 도입하기 전에 확인할 사항은 :doc:`file-server-search`\ 에 정리되어 있습니다.

호스트명과 디렉터리는 예시입니다.

공유 폴더를 읽을 수 있는 서비스 계정(읽기 전용이면 충분합니다)이 있고, ``fess01`` 컨테이너에서 파일 서버의 SMB 포트(445)에 접속할 수 있어야 합니다.

이 글의 제목 순서대로 진행하십시오.

아카이브 디렉터리를 컨테이너에서 읽을 수 있게 하기
==================================================

docker-fess v15.9.0의 ``compose.yaml``\ 에서는 ``fess01``\ 에 볼륨이 정의되어 있지 않습니다.
따라서 호스트의 ``/srv/archive``\ 는 그대로는 컨테이너 안에서 보이지 않습니다.
``compose.yaml``\ 의 ``fess01``\ 에 ``volumes``\ 를 추가하고, 함께 ``environment``\ 에 ``FESS_JAVA_OPTS`` 행을 추가합니다.

.. code-block:: yaml

    services:
      fess01:
        image: ghcr.io/codelibs/fess:15.9.0
        container_name: fess01
        environment:
          - "SEARCH_ENGINE_HTTP_URL=http://search01:9200"
          - "FESS_DICTIONARY_PATH=${FESS_DICTIONARY_PATH:-/usr/share/opensearch/config/dictionary/}"
          - "FESS_JAVA_OPTS=-Duser.timezone=Asia/Tokyo -Dfess.system.day.for.cleanup=10"
        volumes:
          - /srv/archive:/data/archive:ro
        # ports 이후는 원래대로 둠

- ``/srv/archive:/data/archive:ro``\ 는 호스트의 ``/srv/archive``\ 를 컨테이너의 ``/data/archive``\ 에 읽기 전용으로 마운트합니다
- ``-Duser.timezone=Asia/Tokyo``\ 는 나중에 설정하는 작업의 실행 시각을 일본 시간으로 다루기 위한 지정입니다. compose.yaml에도 이미지에도 시간대 지정이 없으므로, 지정하지 않으면 작업이 일본 시간과 어긋난 시각에 실행됩니다
- ``-Dfess.system.day.for.cleanup=10``\ 은 문서 유효 기간(일수)의 기본값을 10일로 합니다. 이유는 뒤의 "주 1회 작업과 문서의 유효 기간"에서 설명합니다

변경한 후에는 컨테이너를 다시 만듭니다.

::

    $ docker compose -f compose.yaml -f compose-opensearch3.yaml up -d

``fess01``\ 이 다시 만들어지므로, 그때까지 [시스템] > [일반]에서 변경한 설정은 사라집니다(:doc:`guide-02`\ 의 "중지와 재개" 참조).
[일반]을 변경하는 작업은 이 절차 뒤에 하십시오.

컨테이너 안의 Fess는 사용자 ``fess``\ (UID 1001)로 실행되고 있습니다.
이 사용자로 파일 목록이 보이는지 확인합니다.

::

    $ docker compose -f compose.yaml -f compose-opensearch3.yaml exec -u fess fess01 ls /data/archive

``Permission denied``\ 가 나오는 경우에는 호스트 쪽 ``/srv/archive`` 이하를 UID 1001에서 읽을 수 있게 하십시오(예를 들어 기타 사용자에게 읽기 권한과 디렉터리 실행 권한을 부여합니다).

라벨 만들기
===========

라벨은 문서의 URL이 정규 표현식과 일치할 때 붙습니다.
크롤링 설정 화면에는 라벨을 고르는 항목이 없으므로(기본적으로 표시되지 않음), 라벨 쪽의 "대상 경로"에서 라벨을 붙일 범위를 지정합니다.

[크롤러] > [라벨] > [새로 만들기]에서 다음 3개를 만듭니다.

.. list-table::
   :header-rows: 1
   :widths: 18 14 68

   * - 이름
     - 값
     - 대상 경로
   * - 포털
     - ``portal``
     - ``https://portal.example.com/.*``
   * - 공유 폴더
     - ``shared``
     - ``smb://fileserver.example.com/shared/.*``
   * - 아카이브
     - ``archive``
     - ``file:/data/archive/.*``

- "이름"은 검색 화면에 표시되는 문자열로, 한글 같은 비ASCII 문자도 사용할 수 있습니다
- "값"에는 영숫자와 밑줄만 사용할 수 있습니다(하이픈이나 한글 등 비ASCII 문자는 입력 오류가 됩니다)
- "대상 경로"는 URL 전체와 일치해야 하므로 끝의 ``.*``\ 를 생략하지 마십시오. 비워 두면 그 라벨은 어떤 문서에도 붙지 않습니다
- "권한"에는 ``{role}guest``\ 가 들어 있습니다. 로그인하지 않은 사용자에게도 라벨이 표시되므로 그대로 둡니다

라벨을 만들기 전에 크롤링한 문서에는 라벨이 붙어 있지 않습니다.
나중에 라벨을 추가하거나 변경한 경우에는 다시 크롤링하거나, [시스템] > [스케줄러]의 "Label Updater"를 [지금 시작]으로 실행하여 기존 문서에 반영합니다.

크롤링 설정 만들기
==================

사내 포털(웹 크롤링)
--------------------

[크롤러] > [웹] > [새로 만들기]에서 다음 항목을 입력하고 [작성]을 클릭합니다.

.. list-table::
   :header-rows: 1
   :widths: 35 65

   * - 항목
     - 값
   * - 이름
     - ``사내 포털``
   * - URL
     - ``https://portal.example.com/``
   * - 크롤링할 URL
     - ``https://portal.example.com/.*``
   * - 크롤링에서 제외할 URL
     - 이미 들어 있는 행 아래에 ``https://portal.example.com/admin/.*`` 추가

"크롤링에서 제외할 URL"에는 이미지나 CSS 등을 제외하는 정규 표현식이 처음부터 들어 있습니다.
지우지 말고 행을 추가하십시오.
"스레드 수"는 ``1``, "간격"은 ``10000``\ 밀리초가 초깃값으로, 포털에 주는 부하를 줄인 설정입니다.

공유 폴더(SMB)와 파일 인증
--------------------------

먼저 [크롤러] > [파일 시스템] > [새로 만들기]에서 다음 설정을 만듭니다.

.. list-table::
   :header-rows: 1
   :widths: 35 65

   * - 항목
     - 값
   * - 이름
     - ``공유 폴더``
   * - 경로
     - ``smb://fileserver.example.com/shared/``
   * - 크롤링할 경로
     - ``smb://fileserver.example.com/shared/.*``
   * - 크롤링에서 제외할 경로
     - ``.*\.tmp$``

파일 크롤링의 초깃값은 "스레드 수"가 ``5``, "간격"이 ``1000``\ 밀리초입니다.

이어서 이 설정에 서비스 계정을 연결합니다.
파일 인증은 파일 크롤링 설정을 골라서 만드는 구조입니다.
파일 크롤링 설정이 하나도 없는 동안에는 [파일 인증] 화면에 [새로 만들기]가 표시되지 않습니다.

[크롤러] > [파일 인증] > [새로 만들기]에서 다음 항목을 입력하고 [작성]을 클릭합니다.

.. list-table::
   :header-rows: 1
   :widths: 35 65

   * - 항목
     - 값
   * - 호스트명
     - ``fileserver.example.com``\ (경로에 쓴 호스트명과 같은 표기)
   * - 포트
     - 빈칸
   * - 스키마
     - ``Samba``
   * - 사용자명 / 비밀번호
     - 서비스 계정의 것
   * - 파라미터
     - 도메인 계정이면 ``domain=EXAMPLE``\ 처럼 도메인명을 지정
   * - 파일 크롤링 설정
     - ``공유 폴더``

"호스트명"은 경로의 호스트명과 글자 그대로 일치해야 합니다.
경로를 IP 주소로 쓴 경우에는 여기에도 IP 주소를 씁니다.
"포트"를 빈칸으로 둔 인증은 ``smb://호스트명/공유명/``\ 처럼 포트를 쓰지 않은 경로에 사용됩니다.

.. note::

   SMB로 크롤링한 파일에는 기본적으로 파일의 접근 권한(ACL)에서 만든 롤이 붙고, 크롤링 설정의 "권한"에 추가됩니다.
   "권한"에 초깃값 ``{role}guest``\ 가 남아 있는 동안에는 로그인하지 않은 사용자를 포함해 모두가 검색할 수 있습니다.
   접근 권한에 따라 검색 결과를 달리 보여 주려면 :doc:`file-server-search`\ 와 :doc:`guide-05`\ 를 참조하십시오.

아카이브(로컬 파일)
-------------------

[크롤러] > [파일 시스템] > [새로 만들기]에서 다음 설정을 만듭니다.
경로는 컨테이너 안의 경로로 지정합니다.

.. list-table::
   :header-rows: 1
   :widths: 35 65

   * - 항목
     - 값
   * - 이름
     - ``아카이브``
   * - 경로
     - ``file:/data/archive/``
   * - 크롤링할 경로
     - ``file:/data/archive/.*``
   * - 크롤링에서 제외할 경로
     - ``.*\.(log|bak)$``

로컬 파일은 ``file:/data/archive/``\ 처럼 ``file:`` 뒤에 슬래시 하나로 씁니다.
크롤러가 찾은 파일의 URL은 ``file:/data/archive/2020/report.pdf`` 형태가 되며, "크롤링할 경로"는 이 URL과 대조됩니다.
``file:///data/archive/.*``\ 로 쓰면 어떤 파일과도 일치하지 않아 한 건도 등록되지 않습니다.

설정별로 작업 만들기
====================

스케줄러의 "Default Crawler"는 유효한 크롤링 설정을 한꺼번에 매일 0:00에 실행합니다.
대상별로 실행 시각을 바꾸려면 크롤링 설정마다 작업을 만듭니다.

1. [크롤러] > [웹]에서 "사내 포털"을 클릭하고, 상세 화면의 [새 작업 작성]을 클릭합니다
2. 작업 작성 화면이 열리며, "이름"에는 ``Web Crawler - 사내 포털``, "스크립트"에는 이 설정만 크롤링하는 내용이 들어 있습니다
3. "스케줄"은 비어 있으므로 cron 식을 입력하고 [작성]을 클릭합니다
4. [크롤러] > [파일 시스템]의 "공유 폴더"와 "아카이브"에서도 같은 조작을 합니다(이름은 ``File Crawler - 공유 폴더``\ 와 같이 됩니다)

.. list-table::
   :header-rows: 1
   :widths: 40 25 35

   * - 작업
     - 스케줄
     - 의미
   * - ``Web Crawler - 사내 포털``
     - ``0 2 * * *``
     - 매일 2:00
   * - ``File Crawler - 공유 폴더``
     - ``0 3 * * *``
     - 매일 3:00
   * - ``File Crawler - 아카이브``
     - ``0 4 * * 0``
     - 매주 일요일 4:00

cron 식은 "분 시 일 월 요일" 순서이며, 요일의 ``0``\ 은 일요일입니다.

마지막으로 "Default Crawler"가 같은 설정을 0:00에 다시 크롤링하지 않도록 합니다.
[시스템] > [스케줄러]에서 "Default Crawler"를 클릭하고, [편집]에서 "스케줄"을 비운 뒤 [갱신]을 클릭합니다.
"상태"의 "유효"를 해제하지 않고 두면, 모든 설정을 한꺼번에 크롤링하고 싶을 때 [지금 시작]으로 실행할 수 있습니다(무효로 하면 [지금 시작]이 표시되지 않습니다).

주 1회 작업과 문서의 유효 기간
------------------------------

크롤링으로 등록된 문서에는 유효 기간이 붙고, 기간이 지나면 "Doc Purger" 작업(매분 실행)이 인덱스에서 삭제합니다.
유효 기간은 크롤링을 시작한 시각부터 [시스템] > [일반]의 "이전 문서 삭제" 일수만큼 지난 시점이며, 초깃값은 ``3``\ 일입니다.
다음 크롤링에서 같은 파일이 발견되면 유효 기간이 연장됩니다.

초깃값 그대로라면 일요일에만 크롤링하는 아카이브의 문서는 수요일에는 검색할 수 없게 됩니다.
따라서 이 일수를 가장 긴 크롤링 간격(7일)보다 크게 해야 합니다.
이 글에서는 작업이 한 번 실패해도 사라지지 않도록 여유를 두어 ``10``\ 일로 하고 있습니다.

- Docker 환경에서는 앞에서 설명한 ``-Dfess.system.day.for.cleanup=10``\ 이 이 초깃값이 됩니다. [일반]의 값은 ``fess01``\ 을 다시 만들면 사라지므로 compose.yaml에 써 두는 편이 확실합니다
- Docker 이외의 환경에서는 [일반]의 "이전 문서 삭제"를 ``10``\ 으로 하고 [갱신]을 클릭합니다

이 일수를 늘리면 파일 서버에서 삭제된 파일도, 마지막으로 발견된 크롤링부터 최대 그 일수 동안 검색 결과에 남습니다.

실행하고 결과 확인하기
======================

작업 실행하기
-------------

다음 날까지 기다리지 말고 [시스템] > [스케줄러]에서 3개의 작업을 차례로 클릭하여 각각 [지금 시작]을 클릭합니다.

완료 확인하기
-------------

1. [시스템 정보] > [작업 로그]에서 3개 작업의 "상태"가 "실행 중"에서 "OK"가 될 때까지 기다립니다. "실패"인 경우에는 행을 클릭하여 "결과"를 확인합니다
2. [시스템 정보] > [크롤링 정보]에서 각 세션의 "인덱스 크기 (웹/파일)"를 보고, 등록 건수가 예상에 가까운지 확인합니다
3. 건수가 적은 경우에는 [시스템 정보] > [장애 URL]을 엽니다. 가져오지 못한 URL과 오류 종류, 로그가 기록되어 있습니다

흔한 원인은 다음과 같습니다.

- 공유 폴더가 0건이고 장애 URL에 공유의 경로가 기록되어 있음: 파일 인증의 "호스트명"과 경로의 표기, "파일 크롤링 설정"의 선택, 비밀번호를 다시 확인합니다. 로그에 접속 오류가 나와 있으면 컨테이너에서 파일 서버의 이름을 해석할 수 있는지, 445번 포트에 닿는지 확인합니다
- 아카이브가 0건이고 장애 URL도 비어 있음: 경로를 ``file:///``\ 로 쓰지 않았는지, "크롤링할 경로"가 경로와 같은 형태인지 다시 확인합니다
- 아카이브에서 읽기 오류가 발생함: 앞에서 설명한 ``exec -u fess`` 명령으로 컨테이너에서 파일을 읽을 수 있는지 확인합니다

라벨로 범위 좁히기
------------------

``http://localhost:8080/``\ 에서 3곳 모두에 들어 있을 만한 단어를 검색합니다.
결과에는 포털의 페이지, 공유 폴더의 Office 문서, 아카이브의 PDF 등이 관련도 순으로 섞여서 나열됩니다.

라벨로 범위를 좁히는 기능은 15.9의 검색 화면(테마 ``bootstrap``)에서 두 곳에 있습니다.

- 검색 결과 옆에 표시되는 "라벨" 목록: 결과에 포함된 라벨이 건수와 함께 나열되며, 클릭하면 그 라벨로 범위가 좁혀집니다
- 검색창 오른쪽에 있는 톱니바퀴 버튼: "검색 옵션"이 열리며, "레이블" 목록에서 하나 이상을 골라 [검색]을 클릭합니다. 여러 개를 고르면 그중 어느 라벨이든 붙은 문서가 대상이 되고, 아무것도 고르지 않으면 전체가 대상입니다

범위를 좁혔을 때의 URL에는 ``fields.label=shared`` 같은 파라미터가 붙습니다.
검색 결과 옆에 "라벨"이 나오지 않거나, 범위를 좁히면 0건이 되는 경우에는 라벨을 만들기 전에 크롤링하지 않았는지 확인합니다("Label Updater"를 실행하면 해결됩니다).
"검색 옵션"에 "레이블" 목록이 나오지 않는 경우에는 라벨의 "권한"에 검색하는 사람의 롤이 포함되어 있는지 확인합니다.

검색 결과의 링크와 경로 매핑
============================

공유 폴더나 아카이브의 검색 결과를 클릭하면 Fess가 파일을 읽어 브라우저에 돌려줍니다.
이는 [일반]의 "Search File Proxy"에 의한 동작으로, 초기 상태에서 유효합니다.
브라우저에서 ``smb://``\ 나 ``file:`` URL을 직접 열 수 없어도 파일을 열 수 있습니다.

아카이브와 같은 파일을 사내 웹 서버(여기서는 ``https://archive.example.com/``)에서도 공개하고 있고 그쪽을 열게 하고 싶다면, 경로 매핑으로 URL을 변환합니다.

[크롤러] > [경로 매핑] > [새로 만들기]에서 다음 항목을 입력하고 [작성]을 클릭합니다.

.. list-table::
   :header-rows: 1
   :widths: 30 70

   * - 항목
     - 값
   * - 정규 표현식
     - ``^file:/data/archive/(.*)$``
   * - 치환
     - ``https://archive.example.com/$1``
   * - 처리 종류
     - 표시

"처리 종류"는 처음에 "크롤링"이 선택되어 있으므로 반드시 "표시"로 바꿉니다.

- 표시: 인덱스의 URL은 ``file:/data/archive/...`` 그대로 두고, 검색 결과의 링크를 클릭했을 때의 이동 대상만 바꿉니다. 만든 시점부터 적용되며 다시 크롤링할 필요가 없습니다
- 크롤링: 인덱스에 저장하는 URL 자체를 다시 씁니다. 다시 크롤링할 때까지 적용되지 않으며, 라벨의 "대상 경로"도 다시 쓴 뒤의 ``https://`` URL에 맞춰야 합니다

설정한 뒤 검색하고 아카이브의 결과를 클릭하면 ``https://archive.example.com/`` 웹 서버가 열리는지 확인합니다.
