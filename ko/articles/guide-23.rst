======================================
전사 확대 진행 방법: 단계별 체크리스트
======================================

들어가며
========

Fess 시범 운영이 잘 되어 전사로 확대하게 되었을 때 고민되는 것은 기능 자체보다 순서입니다.
설정에 따라서는 나중 단계로 미루면 되돌리는 작업이 커집니다.
예를 들어 인증 정보를 등록한 뒤에 암호 키를 바꾸면 저장된 값을 복호화할 수 없게 되고, 문서의 권한을 나중에 바꾸면 다시 크롤링해야 합니다.

이 글에서는 Fess 15.9를 전사에 전개하는 순서를 단계별로 보여 줍니다.
각 단계마다 설정할 것, 확인할 것, 다음 단계로 넘어가도 되는지 판단하는 지표를 듭니다.
지표로는 관리 화면의 [시스템 정보] > [검색 로그]에 있는 분석 리포트를 사용합니다.
개별 기능의 절차는 설명하지 않고, 그 기능을 다루는 글로 링크합니다.

구성 요소와 담당 글
===================

전사 전개에서 다루는 구성 요소와, 각각을 자세히 다루는 글은 다음과 같습니다.

- Fess 본체: 검색 화면, 관리 화면, API, 스케줄러를 제공합니다. 전체 모습은 :doc:`guide-01`, 메모리와 서버 수 확장은 :doc:`guide-14`
- OpenSearch: 문서 인덱스뿐 아니라 크롤링 설정, 사용자, 작업 로그, 검색 로그도 저장합니다. 분리와 클러스터화는 :doc:`guide-14`, 스냅샷은 :doc:`guide-10`
- 크롤러 등의 자식 프로세스: 크롤링, 서제스트 생성, 썸네일 생성, 청크 처리는 작업마다 Fess 본체와는 별도의 JVM에서 실행됩니다. 힙 설정은 :doc:`guide-14`
- 플러그인: 데이터 저장소(``fess-ds-*``), SSO(``fess-sso-*``), LLM과 임베딩(``fess-llm-*``), MCP와 멀티모달 검색(``fess-webapp-*``) 등. Fess와 같은 마이너 버전(15.9.x)을 설치하고, 설치나 삭제 후에는 Fess를 재시작합니다. 만드는 방법은 :doc:`guide-17`
- LLM과 임베딩 모델(선택): AI 검색 모드와 시맨틱 검색에서 사용하는 외부 서비스, 또는 Ollama 등의 서버입니다. 설정은 :doc:`guide-18`, :doc:`guide-19`

OpenSearch에 저장되지 않는 것은 Fess 서버마다 관리합니다.
[시스템] > [일반]의 설정(``system.properties``), ``fess_config.properties``\ (암호 키 ``app.cipher.key`` 포함), 설치한 플러그인의 세 가지입니다.
이들을 보관하는 방법은 :doc:`guide-10`, 코드로 관리하는 방법은 :doc:`guide-16`\ 을 참고하십시오.

단계 목록
=========

.. list-table::
   :header-rows: 1
   :widths: 22 40 38

   * - 단계
     - 목적
     - 다음으로 넘어가는 기준
   * - 1. 시범 운영
     - 소수의 사용자에게 검색하게 하여 무엇을 찾는지 파악한다
     - 인기 검색어와 제로 히트 검색어를 기록으로 남겼다
   * - 2. 첫 정보원 공개
     - 권한을 붙여 첫 번째 정보원을 공개하고 운영의 기본을 갖춘다
     - 사용자 수와 클릭률의 기준값을 기록했다
   * - 3. SSO와 로그인
     - 사내 ID로 로그인하게 하고 그룹에 따라 결과를 다르게 보여 준다
     - "역할·그룹별 검색 수"에 IdP의 그룹이 나타난다
   * - 4. 정보원 늘리기
     - SaaS, 클라우드 스토리지, 데이터베이스를 추가한다
     - 문서 부족이 원인이었던 제로 히트 검색어가 사라진다
   * - 5. 품질 개선 사이클
     - 검색 로그에서 문제 있는 검색어를 찾아 고친다
     - 이전 기간과 비교해 고친 지표가 나빠지지 않았다
   * - 6. 규모 확장과 자동화
     - 문서와 사용자 증가에 대비하고 환경을 재현할 수 있게 한다
     - [성능] 탭의 응답 시간이 사용자가 늘어도 확장 전보다 나빠지지 않았다
   * - 7. AI 기능
     - AI 검색 모드, 시맨틱 검색, MCP를 추가한다
     - [AI 채팅] 탭에 요청이 기록되고, 오류율이 도입 직후보다 오르지 않았다

어느 단계든 이전 단계의 설정을 전제로 합니다.
특히 단계 2와 단계 3은 나중에 바꾸면 다시 크롤링해야 하는 설정을 포함하므로 순서를 바꾸지 마십시오.

단계 1: 시범 운영
=================

검증용 Fess를 구축하여 일부 부서에서 사용하게 합니다.
이 단계의 목적은 사용자가 무엇을 찾고 있는지를 검색 로그로 모으는 것입니다.

**설정할 것**

- :doc:`guide-02`\ 의 절차대로 docker-fess의 ``v15.9.0`` 태그의 Compose 파일로 기동하고, 처음 로그인할 때 비밀번호를 변경한다
- 대상을 하나의 사이트나 하나의 폴더로 좁혀 크롤링 설정을 만든다
- [시스템] > [일반]의 "검색 로그"와 "사용자 로그"가 활성화되어 있는지 확인한다(둘 다 기본값은 활성). "사용자 로그"가 비활성이면 사용자 수가 집계되지 않는다

**확인할 것**

- [시스템 정보] > [작업 로그]에서 크롤링 작업이 "OK"가 되고, [시스템 정보] > [크롤링 정보]에서 등록 건수가 0이 아니다
- 건수가 적으면 [시스템 정보] > [장애 URL]을 확인한다(:doc:`guide-02`)

**다음으로 넘어가는 기준**

- [검색 로그]의 [개요] 탭에 시범 기간의 검색 수, 사용자 수, 인기 검색어, 제로 히트 검색어가 표시된다
- 제로 히트 검색어를 클릭해 [로그] 탭에서 실제 검색을 확인한 다음, :doc:`guide-08`\ 의 표에 따라 원인을 "다른 표현", "정식 용어로 유도", "문서 없음"으로 나눈다
- "문서 없음"으로 나눈 검색어는 단계 2와 단계 4에서 추가할 정보원의 후보로 삼는다. 표의 CSV를 내려받아 보관해 둔다

단계 2: 첫 정보원 공개
======================

전사 사용자가 사용할 정보원을 하나 골라 권한을 붙여 공개합니다.
동시에 운영 환경에 필요한 모니터링과 백업을 갖춥니다.

**설정할 것**

- 암호 키 ``app.cipher.key``\ 는 웹 인증·파일 인증이나 데이터 저장소의 파라미터에 인증 정보를 등록하기 전에 정한다. 등록 후에 바꾸면 저장된 값을 복호화할 수 없다(:doc:`guide-16`, :doc:`guide-10`)
- 웹 사이트와 공유 폴더의 크롤링 설정, 파일 인증, 라벨을 만든다(:doc:`guide-04`). 파일 서버의 ACL을 검색 결과에 반영하려면 :doc:`file-server-search`
- 권한 설계를 정한다(:doc:`guide-05`). 새 크롤링 설정과 라벨에는 권한 ``{role}guest``\ 가 들어 있어, 그대로 두면 로그인하지 않은 사용자에게도 보인다. 부서별로 나누어 보여 줄 문서는 이 값을 지운 뒤 ``{group}`` 등을 적는다
- ``{group}``\ 에 적는 그룹 이름은 단계 3에서 IdP로부터 전달되는 이름에 맞춰 둔다. 나중에 이름을 바꾸면 권한을 다시 쓰고 다시 크롤링해야 한다
- 주 1회 등 작업으로 실행하는 크롤링 설정이 있으면 [일반]의 "이전 문서 삭제"(기본값 3일)를 크롤링 간격보다 길게 한다(:doc:`guide-04`)
- 모니터링, 알림, 백업을 설정한다(:doc:`guide-10`). ``/api/v2/health``\ 를 외부 모니터링 도구에서 호출하고, [일반]의 "알림 메일"이나 "Slack Webhook URLs"를 설정하고, [시스템 정보] > [백업]의 파일을 관리 API로 매일 가져온다
- Docker의 경우 [일반]의 설정은 ``fess01`` 컨테이너 안의 ``system.properties``\ 에 저장되며, ``down``\ 으로 컨테이너를 다시 만들면 사라진다. 백업에 포함하거나 ``FESS_JAVA_OPTS``\ 로 전달한다(:doc:`guide-02`, :doc:`guide-16`)
- 필요에 따라 사내 포털에 검색창을 둔다(:doc:`guide-03`)

**확인할 것**

- 부서가 다른 사용자로 로그인하면 보이는 문서가 달라진다. 부서용 문서에 기록된 권한에 초기값인 guest 역할이 남아 있지 않다(확인 방법은 :doc:`guide-05`)
- ``/api/v2/health``\ 가 200을 반환하고, [일반]의 [테스트 메일 보내기]로 메일이 도착한다
- 백업 스크립트를 한 번 손으로 실행해 가져온 파일이 비어 있지 않다(:doc:`guide-10`)

**다음으로 넘어가는 기준**

[검색 로그]로는 이 단계의 모니터링이나 백업 상태를 알 수 없습니다.
그것들은 위의 "확인할 것"으로 판단합니다.
검색 로그에서는 공개 후 이용 상황의 기준값을 잡습니다.

- [개요] 탭에서 공개 후 기간의 검색 수, 사용자 수, 제로 히트율, 클릭률을 확인하고 CSV로 남긴다. 이후 단계에서는 이 값과 "이전 기간과 비교"로 비교한다
- [클릭] 탭의 "클릭 수가 많은 URL"에 공개한 정보원의 URL이 나열된다
- [일반]의 "이전 검색 로그 삭제"에 일수를 지정하면 그보다 오래된 로그는 비교에 쓸 수 없다(기본값 ``-1``\ 은 삭제하지 않음). 보관 기간을 정해 둔다

단계 3: SSO와 로그인
====================

사내 ID 기반(IdP)으로 로그인하게 하고, IdP의 그룹에 따라 검색 결과를 다르게 보여 줍니다.

여기서 말하는 SSO는 Fess 15.9에서 플러그인으로 제공되는 4가지 방식입니다.
Entra ID는 ``fess-sso-entraid``, OpenID Connect는 ``fess-sso-oidc``\ ("SSO Type"은 ``oic``), SAML은 ``fess-sso-saml``, SPNEGO는 ``fess-sso-spnego``\ 를 사용합니다.
Docker 이미지에는 4개 모두 들어 있지만 ``-slim`` 이미지에는 들어 있지 않습니다.
ZIP·RPM·DEB 버전에서는 [시스템] > [플러그인]이나 ``bin/fess-setup``\ 으로 설치합니다.

LDAP는 SSO가 아닙니다.
[일반]의 LDAP 설정은 Fess 로그인 화면에서 입력된 ID와 비밀번호를 Active Directory 등으로 확인하고 소속 그룹을 가져오는 기능입니다(:doc:`guide-05`).
SPNEGO는 그룹을 가져올 때 이 LDAP 설정을 사용합니다.

**설정할 것**

- 플러그인을 설치하고 Fess를 재시작한 뒤, [일반]의 "SSO Type"과 IdP 정보를 설정한다. IdP에 등록할 반환 주소는 ``https://<Fess 호스트>/sso/``\ (:doc:`guide-15`)
- TLS를 종단하는 리버스 프록시 뒤에 두는 경우에는 외부 스킴과 포트를 Fess에 알려 준다(:doc:`guide-15`)
- 로그인하지 않은 사용자가 검색하지 못하게 하려면 [일반]의 "로그인 필요"를 활성화한다

"로그인 필요"는 검색 화면 외에도 영향을 줍니다.

- ``/api/v2/``\ 의 검색 API는 로그인 세션이나 유효한 액세스 토큰이 없는 호출에 401을 반환한다. 업무 시스템에서의 호출에는 토큰을 준비한다(:doc:`guide-11`)
- MCP의 기본값 ``mcp.auth.mode=none``\ 에서는 ``/mcp``\ 가 AI 에이전트의 호출을 HTTP 403으로 거부한다. 사용하는 경우에는 액세스 토큰으로 인증하는 설정으로 바꾼다(:doc:`guide-20`)

**확인할 것**

- ``/sso/``\ 를 열어 IdP를 거쳐 로그인할 수 있고, 부서마다 보이는 문서가 단계 2의 설계대로 달라진다(:doc:`guide-15`)
- Fess를 여러 대로 운영하는 경우에는 로드 밸런서에서 스티키 세션을 활성화해 두었다. 15.9의 로그인 세션은 각 Fess의 메모리에 있다

**다음으로 넘어가는 기준**

- [검색 로그]의 [사용자·환경] 탭에 있는 "역할·그룹별 검색 수"에 IdP에서 전달된 그룹의 행이 ``{group}<그룹 이름>`` 형식으로 나열된다
- 그룹 행이 나타나지 않으면, 사용자가 로그인하지 않고 검색하고 있거나(``{role}guest`` 행에 집계됨) 그룹이 Fess에 전달되지 않고 있다
- [개요] 탭의 사용자 수가 단계 2의 기준값에서 크게 줄지 않았다. 로그인 도입으로 이용을 그만둔 부서가 없는지 "역할·그룹별 검색 수"의 "사용자 수" 열로 확인한다

단계 4: 정보원 늘리기
=====================

웹 사이트와 파일 서버 이외의 정보원을 데이터 저장소 플러그인으로 추가합니다.
모든 정보원에 공통된 절차(플러그인 설치, 파라미터와 스크립트, 권한, 작업, 결과 확인 방법)는 :doc:`datastore-basics`\ 에 정리되어 있습니다.
먼저 이 글을 읽으십시오.

**설정할 것**

- 정보원마다 플러그인을 설치하고 재시작한다

  - Git, Confluence·Jira, Slack: ``fess-ds-git``, ``fess-ds-atlassian``, ``fess-ds-slack``\ (:doc:`guide-06`)
  - Google Drive, SharePoint·OneDrive, Box: ``fess-ds-gsuite``, ``fess-ds-microsoft365``, ``fess-ds-box``\ (:doc:`guide-07`)
  - 데이터베이스, CSV, Salesforce: ``fess-ds-db``, ``fess-ds-csv``, ``fess-ds-salesforce``\ (:doc:`guide-12`)
  - 대응하는 플러그인이 없는 정보원은 직접 플러그인을 만든다(:doc:`guide-17`)

- 데이터 저장소 설정에도 ``{role}guest``\ 가 들어 있다. 정보원의 권한을 이어받을지, 단계 2의 ``{group}``\ 으로 적을지를 설정마다 정한다
- 설정마다 [새 작업 작성]으로 작업을 나누어, API 속도 제한이나 인증 정보의 만료를 정보원별로 다룰 수 있게 한다
- 정보원마다 라벨을 붙여 검색 화면에서 좁혀 볼 수 있게 한다. 데이터 저장소 설정에는 라벨 항목이 없으므로 스크립트나 라벨의 "대상 경로"로 붙인다(:doc:`datastore-basics`)

**확인할 것**

- 데이터 저장소 작업은 커넥터에서 오류가 나도 "OK"로 끝나는 경우가 있다. [크롤링 정보]의 "인덱스 크기 (데이터 저장소)", [장애 URL], ``fess-crawler.log``\ 를 함께 확인한다(:doc:`datastore-basics`)
- 권한을 이어받은 정보원에서는 권한이 다른 사용자로 검색하면 보이는 문서가 달라진다

**다음으로 넘어가는 기준**

- 단계 1과 단계 2에서 "문서 없음"으로 나눈 제로 히트 검색어가, 정보원을 추가한 이후 기간의 [검색어] 탭 제로 히트 검색어에서 사라진다
- [클릭] 탭의 "클릭 수가 많은 URL"에 추가한 정보원의 문서가 나타난다. 나타나지 않는 정보원은 검색되지 않았거나 결과 상위에 나오지 않은 것이다. 후자는 단계 5에서 다룬다

단계 5: 품질 개선 사이클
========================

정보원이 갖추어지면 검색 로그를 정기적으로 보고 문제 있는 검색어를 고칩니다.
고치는 방법을 고르는 법과 반영 절차는 :doc:`guide-08`\ 에서 다룹니다.

**설정할 것**

- 제로 히트 검색어에는 동의어나 관련 쿼리, 하위에 묻힌 문서에는 키 매치나 문서 부스트를 사용한다(:doc:`guide-08`). 동의어 사전을 바꾸면 [시스템 정보] > [유지보수]에서 문서 인덱스를 다시 로드한다
- 일본어·영어·중국어가 섞인 문서에서 누락이 있으면 언어별 필드와 사전을 확인한다(:doc:`guide-09`)
- 기본 제공 리포트에 없는 집계(검색어별로 열린 URL, 역할별 제로 히트 검색어, 장기간의 월별 추이 등)가 필요해지면 OpenSearch Dashboards를 사용한다(:doc:`guide-22`)
- 사전이나 키 매치 설정을 코드로 관리하려면 :doc:`guide-16`

**확인할 것**

- 고친 검색어로 검색 화면에서 검색하면 목표한 문서가 검색되거나 상위에 나온다
- 키 매치는 상세 화면의 "URL" 항목에 대상 문서가 표시된다(:doc:`guide-08`)

**다음으로 넘어가는 기준**

이 단계에는 끝이 없으며 반복해서 진행합니다.
한 번의 개선 효과는 다음과 같이 확인합니다.

- 기간을 "사용자 지정"으로 하여 변경한 날의 다음 날부터 잡고, "이전 기간과 비교"를 활성화한다
- 제로 히트 검색어를 고친 경우에는 [개요] 탭의 제로 히트율과 [검색어] 탭의 제로 히트 검색어를, 순위를 고친 경우에는 [검색어] 탭의 평균 클릭 순위와 [클릭] 탭의 클릭 순위 분포를 본다
- 고친 검색어가 목록에서 사라지고 전체 지표가 이전 기간보다 나빠지지 않았다면 그 변경은 유지한다

단계 6: 규모 확장과 자동화
==========================

문서나 사용자가 늘면 무엇이 부족해졌는지 확인한 뒤 확장합니다.
아울러 같은 환경을 다시 만들 수 있게 합니다.

**설정할 것**

- 무엇이 부족한지 증상별로 확인한다(:doc:`guide-14`). ``fess-crawler.log``\ 의 OutOfMemoryError는 크롤러 JVM(``jvm.crawler.options``)의 부족이며, Fess 본체의 힙(``FESS_HEAP_SIZE``)을 늘려도 해결되지 않는다
- OpenSearch를 별도 서버로 분리하기, 3대 클러스터로 만들기, Fess를 여러 대로 늘리기 순으로 검토한다(:doc:`guide-14`)
- Fess를 여러 대로 운영하는 경우에는 크롤링을 1대에 맡긴다. ``scheduler.target.name``\ 과 [시스템] > [스케줄러]의 "대상"을 모두 설정한다(:doc:`guide-14`)
- 여러 대에서는 ``app.cipher.key``, ``fess_config.properties``, [일반]의 설정, 플러그인을 모든 서버에서 맞춘다
- Docker 이미지의 태그와 플러그인 버전을 고정하고, 설정을 fessctl과 관리 API로 적용할 수 있게 한다(:doc:`guide-16`)
- Fess 하나를 여러 조직이 나누어 쓰는 경우에는 가상 호스트와 역할을 조합한다. 가상 호스트만으로는 접근 제어가 되지 않는다(:doc:`guide-13`)

**확인할 것**

- 확장 전후로 ``/api/admin/stats``\ 의 힙 사용률과 [시스템 정보] > [작업 로그]의 크롤링 소요 시간을 비교한다(:doc:`guide-10`)
- 여러 대에서는 어느 서버로 열어도 같은 검색 결과가 나오고, 크롤링은 담당 서버에서만 실행된다. 다른 서버에서 [지금 시작]을 클릭해도 실행되지 않는다(:doc:`guide-14`)
- 다시 만든 환경에 백업에서 설정을 복원할 수 있다(:doc:`guide-10`)

**다음으로 넘어가는 기준**

- [검색 로그]의 [성능] 탭에서 응답 시간의 중앙값·p95·p99가 확장 전보다 낮아졌거나, 사용자가 늘어도 오르지 않았다
- "응답이 느린 검색어"에 나열된 검색어로 검색해 특정 검색어만 느린지 전체가 느린지 구분한다

참고로, 로그인 세션을 OpenSearch에 저장해 여러 대에서 공유하는 기능은 15.10 이후에 사용할 수 있습니다.
15.9에서는 앞서 설명한 스티키 세션으로 운영합니다.

단계 7: AI 기능
===============

AI 기능은 기능마다 필요한 준비가 다릅니다.
목적에 맞는 것부터 추가합니다.

**AI 검색 모드(RAG)**

- 사용자의 질문에 사내 문서를 근거로 LLM이 답하는 기능입니다(:doc:`guide-19`)
- 벡터 검색은 필요하지 않습니다. 근거 문서는 일반 검색으로 모으므로 단계 2~3의 권한이 그대로 적용되며, 사용자가 볼 수 없는 문서는 답변에 사용되지 않습니다
- ``fess_config.properties``\ 의 ``rag.chat.enabled=true``\ (기본값은 ``false``, 관리 화면에 항목 없음), ``fess-llm-*`` 플러그인, [일반]의 "LLM 제공자" 세 가지가 필요합니다
- 사용할 수 있는 사용자는 [일반]의 "채팅 권한"으로 제한할 수 있습니다

**시맨틱 검색과 멀티모달 검색**

- 시맨틱 검색은 키워드가 일치하지 않아도 의미가 가까운 문서를 찾습니다(:doc:`guide-18`). 임베딩 제공자는 ``content_chunker.embedding.name``\ 으로 선택합니다. 기본값 ``opensearch``\ 는 OpenSearch ML Commons의 모델을 사용하며, ``ollama``·``openai``·``gemini``·``bedrock``\ 은 대응하는 ``fess-llm-*`` 플러그인이 필요합니다
- 기존 환경에서 활성화하는 경우에는 인덱스를 다시 만든 뒤 모든 문서의 벡터를 생성합니다. OpenAI 등 종량 과금 모델에서는 첫 처리에서 모든 문서분의 요금이 발생합니다
- 멀티모달 검색은 플러그인 ``fess-webapp-multimodal``\ 과 CLIP 서버를 사용해 텍스트로 이미지를 찾습니다(:doc:`guide-21`)
- 이 두 가지는 하나의 Fess에서 동시에 사용할 수 없습니다. 둘 다 필요한 경우에는 Fess를 나누어 구축합니다

**MCP**

- AI 에이전트가 Fess를 검색하게 하는 기능입니다(:doc:`guide-20`). 플러그인 ``fess-webapp-mcp``\ 를 설치하면 ``/mcp``\ 를 사용할 수 있습니다
- 기본값 ``mcp.auth.mode=none``\ 에서는 ``/mcp``\ 에 도달할 수 있는 사람은 누구나 게스트로 검색할 수 있습니다. 사내에 공개하기 전에 액세스 토큰 등으로 인증하는 설정으로 바꿉니다

**확인할 것**

- AI 검색 모드: 검색 화면의 [AI 검색]에서 질문하면 답변과 출처가 표시된다. 권한이 다른 사용자로 확인하면 볼 수 없는 문서가 출처에 나타나지 않는다(:doc:`guide-19`)
- 시맨틱 검색·멀티모달 검색: 문서에 벡터가 기록되고, 검색 API 응답에서 벡터 검색이 사용되고 있다(:doc:`guide-18`, :doc:`guide-21`)
- MCP: 인증 설정을 바꾼 뒤 토큰 없는 호출이 거부된다(:doc:`guide-20`)

**다음으로 넘어가는 기준**

- AI 검색 모드는 [검색 로그]의 [AI 채팅] 탭에서 요청 수, 사용자 수, 오류율, 평균 응답 시간을 본다. 토큰 수는 LLM 플러그인이 보고한 경우에만 기록되며, 질문과 답변의 내용은 기록되지 않는다
- 시맨틱 검색은 도입한 날의 다음 날부터의 기간으로 "이전 기간과 비교"를 활성화하고, 제로 히트율, 클릭률, [성능] 탭의 응답 시간을 비교한다
- MCP와 멀티모달 검색에는 [검색 로그]에 전용 지표가 없다. 위의 "확인할 것"과 이용 부서의 보고로 판단한다
