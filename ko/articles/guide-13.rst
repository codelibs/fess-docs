=====================================
하나의 Fess를 여러 조직에서 나눠 쓰기
=====================================

들어가며
========

그룹사나 부서마다 검색 서비스를 제공하려고 조직 수만큼 Fess를 구축하면, 서버도 크롤링 설정 관리도 조직 수만큼 늘어납니다.
Fess의 가상 호스트 기능을 사용하면 하나의 Fess를 여러 호스트명으로 공개하고, 호스트명마다 검색 대상, 라벨, 검색 화면을 전환할 수 있습니다.

다만 가상 호스트는 "어떤 호스트명으로 접속했는가"에 따라 표시를 구분하는 기능이며, 접근 제어가 아닙니다.
다른 조직의 문서를 확실히 보이지 않게 하려면 역할에 의한 권한 설정과 로그인을 함께 사용해야 합니다.

이 글에서는 A사와 B사라는 2개의 테넌트를 예로, Fess 15.9에서 다음 내용을 차례로 설정합니다.

- [일반]의 "가상 호스트"에서 호스트명과 테넌트를 연결한다
- 크롤링 설정과 라벨에 가상 호스트와 권한을 지정하여 테넌트의 문서를 나눈다
- 가상 호스트명과 같은 이름의 테마로 테넌트마다 검색 화면을 바꾼다
- 테넌트의 사용자로 로그인하여 다른 테넌트의 문서가 보이지 않는지 확인한다
- 테넌트의 추가와 삭제를 올바른 순서로 수행한다

역할, 그룹, 사용자의 기본은 :doc:`guide-05`\ 에서 다룹니다.

먼저 알아 둘 것: 가상 호스트는 접근 제어가 아니다
=================================================

Fess는 요청마다 [일반]의 "가상 호스트"에 적은 행을 위에서부터 차례로 평가하여, 지정한 헤더(보통 ``Host``)의 값이 일치한 첫 번째 행의 가상 호스트명(이하 키)을 사용합니다.
키가 정해지면 다음 기능이 그 키로 필터링됩니다.

- 검색 결과: 크롤링 설정의 "가상 호스트"에 그 키를 가진 문서만 반환됩니다(검색 API도 마찬가지입니다)
- 라벨: "가상 호스트" 항목이 그 키인 라벨만 표시됩니다
- 키 매치, 관련 콘텐츠, 관련 쿼리: "가상 호스트" 항목이 그 키인 설정만 사용됩니다
- 검색 화면: 키를 소문자로 바꾼 이름의 테마가 있으면 그 테마로 표시됩니다

반면 어느 행과도 일치하지 않는 요청에서는 이 필터링이 전혀 이루어지지 않습니다.
서버의 IP 주소로 직접 접속한 경우나 리버스 프록시가 ``Host`` 헤더를 바꿔 쓴 경우에는 가상 호스트에 의한 필터링이 사라지고, 권한으로 볼 수 있는 범위 안의 모든 테넌트 문서가 검색 대상이 됩니다.
[일반]의 호스트명 오타나 포트 번호 누락도 오류가 되지 않고 "일치하지 않음"으로 처리됩니다.

따라서 테넌트 간에 문서가 보이지 않게 하려면 다음 두 가지를 함께 사용합니다.

- 각 테넌트 문서의 권한을 그 테넌트의 역할(예: ``{role}tenanta_user``)로만 한정한다
- 검색 화면에 로그인을 필수로 하고, 사용자에게 테넌트의 역할을 할당한다

이 글에서 만드는 구성
=====================

.. list-table::
   :header-rows: 1
   :widths: 16 26 14 18 26

   * - 테넌트
     - 공개 호스트명
     - 키
     - 역할
     - 크롤링 대상
   * - A사
     - ``search-a.example.com``
     - ``tenanta``
     - ``tenanta_user``
     - ``https://portal-a.example.com/``
   * - B사
     - ``search-b.example.com``
     - ``tenantb``
     - ``tenantb_user``
     - ``https://portal-b.example.com/``

키에는 영숫자와 밑줄(``a-zA-Z0-9_``)만 사용할 수 있습니다.
그 밖의 문자는 저장할 때 제거되므로 ``tenant-a``\ 라고 쓰면 키는 ``tenanta``\ 가 되고, 크롤링 설정에 ``tenant-a``\ 라고 써도 일치하지 않습니다.
``admin``, ``common``, ``error``, ``login``, ``profile``\ 은 예약되어 있어 사용할 수 없습니다.

크롤링 설정이나 라벨의 "가상 호스트" 항목은 자유 입력이며, 키와의 대조는 대소문자를 구분합니다.
테마 이름도 소문자만 사용할 수 있으므로, 키는 처음부터 소문자 영숫자로 통일해 두면 실수가 생기지 않습니다.

절차 1: 호스트명과 키를 연결한다
================================

관리 화면의 [시스템] > [일반]을 열고, "가상 호스트"에 한 행에 하나씩 ``헤더명:헤더값=키``\ 를 적은 뒤 업데이트합니다.

::

    Host:search-a.example.com=tenanta
    Host:search-b.example.com=tenantb

헤더 값은 대소문자를 구분하지 않고 완전 일치로 비교됩니다.
브라우저는 표준 포트(80, 443) 이외로 접속하면 ``Host`` 헤더에 포트 번호를 붙이므로, Fess의 포트 8080에 직접 접속하게 하는 경우에는 다음과 같이 포트까지 적습니다.
두 가지 표기를 나란히 적어도 됩니다.

::

    Host:search-a.example.com:8080=tenanta
    Host:search-b.example.com:8080=tenantb

설정은 저장한 시점에 반영되며 재시작은 필요하지 않습니다.
``fess_config.properties``\ 의 ``virtual.host.headers``\ 에도 같은 형식으로 적을 수 있지만, [일반]에 값이 있으면 그쪽이 우선합니다.

리버스 프록시 뒤에 두는 경우에는 브라우저가 보낸 ``Host`` 헤더를 Fess까지 전달합니다.
Nginx는 기본적으로 ``proxy_pass``\ 의 대상을 ``Host``\ 로 하므로 ``proxy_set_header Host $host;``\ 가 필요합니다.

::

    server {
        server_name search-a.example.com search-b.example.com;
        location / {
            proxy_pass http://127.0.0.1:8080;
            proxy_set_header Host $host;
        }
    }

``Host``\ 를 바꿔 쓰는 구성에서는 헤더명에 ``X-Forwarded-Host``\ 를 지정하는 방법도 있습니다(예: ``X-Forwarded-Host:search-a.example.com=tenanta``).

.. warning::

   [일반]의 설정은 컨테이너 안의 ``system.properties``\ 에 저장됩니다.
   docker-fess의 ``fess01``\ 은 볼륨을 가지지 않으므로, ``docker compose down``\ 으로 컨테이너를 다시 만들면 "가상 호스트"의 값도 사라집니다(``stop``, ``start``\ 에서는 남습니다).
   뒤의 절차에서 업로드하는 테마도 컨테이너 안에 놓이므로 마찬가지로 사라집니다.
   설정을 남기는 방법은 `Docker 설치 (상세) <https://fess.codelibs.org/ko/stable/install/install-docker.html>`__\ 를 참조하십시오.

절차 2: 테넌트의 역할과 사용자를 만든다
=======================================

1. [사용자] > [역할]에서 이름이 ``tenanta_user``\ 와 ``tenantb_user``\ 인 역할을 만듭니다.
2. [사용자] > [사용자]에서 각 테넌트의 이용자를 만들고, "역할"에서 그 테넌트의 역할을 선택합니다.
3. [시스템] > [일반]에서 "로그인 필요"를 활성화합니다.

로그인한 사용자에게는 ``{role}guest``\ 가 붙지 않고, 사용자, 그룹, 역할의 권한만으로 검색됩니다.
LDAP이나 SSO의 그룹을 그대로 사용하는 경우에는 역할 대신 ``{group}<그룹명>``\ 으로 지정할 수 있습니다.
권한의 구조와 LDAP 연동은 :doc:`guide-05`, SSO는 :doc:`guide-15`\ 를 참조하십시오.

절차 3: 테넌트마다 라벨을 만든다
================================

라벨은 크롤링할 때 URL이 "대상 경로"와 일치한 문서에 붙습니다.
크롤링보다 먼저 만들어 둡니다.

[크롤러] > [라벨]에서 [새로 만들기]를 누르고, A사용으로 다음과 같이 입력합니다(B사도 같은 방법으로 만듭니다).

.. list-table::
   :header-rows: 1
   :widths: 30 70

   * - 항목
     - 값
   * - 이름
     - ``A사 포털``
   * - 값
     - ``tenanta_docs``\ (영숫자와 밑줄만)
   * - 대상 경로
     - ``https://portal-a\.example\.com/.*``
   * - 권한
     - ``{role}tenanta_user``
   * - 가상 호스트
     - ``tenanta``

새 라벨의 권한에는 ``{role}guest``\ 가 들어 있습니다.
라벨은 이용자가 그 권한의 역할을 가질 때만 표시되므로, ``{role}guest``\ 인 채로 두면 로그인한 테넌트의 사용자에게는 라벨이 표시되지 않습니다.

"가상 호스트"가 비어 있는 라벨은 가상 호스트로 접속했을 때 표시되지 않습니다.
하나의 라벨에 지정할 수 있는 가상 호스트는 하나이므로, 여러 테넌트에 같은 라벨을 보여 주려면 이름과 값이 같은 라벨을 테넌트 수만큼 만들고 각각의 "가상 호스트"에 키를 넣습니다.
키 매치, 관련 콘텐츠, 관련 쿼리도 마찬가지로, "가상 호스트"가 비어 있는 설정은 테넌트의 호스트에서 사용되지 않습니다.

절차 4: 크롤링 설정에 가상 호스트와 권한을 지정한다
===================================================

[크롤러] > [웹]에서 A사용 크롤링 설정을 만듭니다.
파일 시스템과 데이터 저장소의 크롤링 설정에도 같은 두 항목이 있습니다.

.. list-table::
   :header-rows: 1
   :widths: 30 70

   * - 항목
     - 값
   * - 이름
     - ``A사 포털``
   * - URL
     - ``https://portal-a.example.com/``
   * - 크롤링할 URL
     - ``https://portal-a.example.com/.*``
   * - 권한
     - ``{role}tenanta_user``\ (기본으로 들어 있는 ``{role}guest``\ 는 삭제합니다)
   * - 가상 호스트
     - ``tenanta``

``{role}guest``\ 를 남기면 IP 주소로 접속하거나 로그인 전에 접속했을 때 그 문서가 보이게 됩니다.

그룹 전체용 규정집처럼 여러 테넌트에 보여 줄 문서는, 하나의 크롤링 설정의 "가상 호스트"와 "권한"에 각각 한 행씩 두 테넌트분을 적습니다.

::

    가상 호스트:
    tenanta
    tenantb

    권한:
    {role}tenanta_user
    {role}tenantb_user

가상 호스트와 권한은 크롤링할 때 문서에 기록됩니다.
이미 크롤링한 설정에서 이것들을 바꾼 경우, 다시 크롤링할 때까지 기존 문서에는 반영되지 않습니다.

설정을 저장했으면 상세 화면의 [새 작업 작성]으로 테넌트 전용 작업을 만들거나, [시스템] > [스케줄러]의 ``Default Crawler``\ 를 [지금 시작]으로 실행합니다.

절차 5: 테넌트 전용 검색 화면을 준비한다
========================================

Fess 15.9의 검색 화면은 테마로 표시됩니다.
``theme.yml``\ 의 ``name``\ 이 키를 소문자로 바꾼 것과 같은 테마를 설치하면, 그 키의 요청에는 그 테마가 사용됩니다.
기본 테마로 설정할 필요는 없으며, 어느 키와도 일치하지 않는 접속에는 기본 테마가 사용됩니다.

함께 제공되는 ``bootstrap`` 테마를 복제하여 만듭니다.
Docker의 경우에는 다음과 같이 컨테이너에서 꺼냅니다.

::

    $ docker cp fess01:/usr/share/fess/app/themes/bootstrap ./tenanta

1. ``tenanta/theme.yml``\ 의 ``name``\ 을 ``tenanta``\ 로, ``displayName``\ 을 ``A사 검색`` 등으로 바꿉니다.
2. ``assets/styles.css``\ (배색)나 ``assets/logo-head.png``, ``assets/logo.png``\ (로고)를 교체합니다. ``index.html``\ 은 변경할 필요가 없습니다.
3. ``theme.yml``\ 이 ZIP의 루트에 오도록 묶습니다.

   ::

       $ cd tenanta && zip -r ../tenanta.zip .

4. [시스템] > [테마]의 [업로드]에서 ``tenanta.zip``\ 을 업로드합니다.

로그인 화면(``/login/``)은 모든 테넌트에 공통이며, 테마로는 바꿀 수 없습니다.
함께 제공되는 테마를 복제하는 방법의 자세한 내용은 `테마 개발 가이드 <https://fess.codelibs.org/ko/stable/dev/theme-development.html>`__\ 를 참조하십시오.

분리를 확인한다
===============

DNS를 전환하기 전에 로컬의 ``/etc/hosts``\ 에 ``127.0.0.1 search-a.example.com search-b.example.com``\ 을 추가하면, 브라우저에서 ``http://search-a.example.com:8080/``\ 처럼 각 호스트를 시험해 볼 수 있습니다([일반]에는 포트가 붙은 행이 필요합니다).
다음 네 가지 경우를 크롤링 대상에 있는 단어로 검색하여 확인합니다.

.. list-table::
   :header-rows: 1
   :widths: 45 55

   * - 접속
     - 기대하는 결과
   * - A사 사용자로 ``search-a.example.com``\ 에서
     - A사의 문서만 나온다. 라벨은 "A사 포털"뿐. A사의 테마로 표시된다
   * - A사 사용자로 ``search-b.example.com``\ 에서
     - 0건(B사의 문서는 권한이 없고, A사의 문서는 가상 호스트로 제외된다)
   * - A사 사용자로 IP 주소(``http://<서버>:8080/``)에서
     - A사의 문서만 나온다(가상 호스트의 필터링은 없지만 권한으로 보호된다)
   * - 로그인하지 않고 접속
     - 로그인할 때까지 검색할 수 없다

두 테넌트용 공통 문서를 만든 경우에는 1~3행에서 그 문서도 나옵니다.
3행에서 B사의 문서가 나오는 경우에는 어딘가의 크롤링 설정에 ``{role}guest``\ 가 남아 있습니다.
1행에서 0건이 되는 경우에는 [일반]의 행(포트 번호 유무)과 크롤링 설정의 "가상 호스트" 철자를 비교해 봅니다.

검색 API로도 같은 확인을 할 수 있습니다.
[시스템] > [액세스 토큰]에서 권한이 ``{role}tenanta_user``\ 인 토큰을 만들고, ``Host`` 헤더를 바꿔 가며 호출합니다.

::

    $ curl -s -H "Authorization: Bearer <A사 토큰>" \
        -H "Host: search-a.example.com:8080" \
        "http://localhost:8080/api/v2/search?q=fess"
    $ curl -s -H "Authorization: Bearer <A사 토큰>" \
        -H "Host: search-b.example.com:8080" \
        "http://localhost:8080/api/v2/search?q=fess"

첫 번째는 ``response.record_count``\ 가 1 이상, 두 번째는 0이 되면 예상대로입니다.
액세스 토큰은 가상 호스트에 묶여 있지 않으며, 전송 대상 호스트명으로 가상 호스트가 정해집니다.
토큰이 볼 수 있는 범위를 정하는 것은 토큰의 권한이므로, 테넌트의 시스템에 넘기는 토큰에는 반드시 그 테넌트의 역할만 지정합니다.
API 사용법은 :doc:`guide-11`\ 을 참조하십시오.

운영이 시작되면 [시스템 정보] > [검색 로그]의 [사용자·환경] 탭에서 가상 호스트별 검색 수를 확인할 수 있습니다.

테넌트의 추가와 삭제
====================

테넌트를 추가할 때는 뒤의 절차가 앞 절차의 값을 사용하므로 다음 순서로 진행합니다.

1. [일반]의 "가상 호스트"에 행을 추가한다
2. 역할, 사용자, 필요하면 액세스 토큰을 만든다
3. 라벨(가상 호스트와 권한 포함)을 만든다
4. 크롤링 설정(가상 호스트와 권한 포함)을 만들고 크롤링한다
5. 테마를 업로드한다
6. "분리를 확인한다"의 네 가지 경우를 확인한다
7. DNS와 리버스 프록시로 공개한다

테넌트를 삭제할 때는 반대로 이용 입구부터 막습니다.

1. DNS와 리버스 프록시에서 호스트명을 뺀다
2. 크롤링 설정과 그것을 위해 만든 작업([시스템] > [스케줄러])을 삭제한다
3. 인덱스에서 문서를 삭제한다(아래 참조)
4. 액세스 토큰, 사용자, 역할을 삭제한다
5. 라벨, 키 매치 등 그 키의 설정과 테마를 삭제한다
6. [일반]의 "가상 호스트"에서 행을 삭제한다

크롤링 설정을 삭제해도 크롤링한 문서는 인덱스에 남습니다.
문서는 [시스템 정보] > [검색]에서 삭제합니다.
이 화면에서는 역할과 가상 호스트의 필터링이 적용되지 않으므로 모든 테넌트의 문서가 대상입니다.
검색창에 ``label:tenantb_docs``\ 처럼 테넌트의 라벨을 지정하여 검색하고, 건수와 결과가 B사의 문서뿐인지 확인한 뒤 [이 쿼리로 모두 삭제]를 누릅니다.
웹 문서라면 ``site:portal-b.example.com``\ 처럼 URL의 앞부분으로 지정할 수도 있습니다.

``virtual_host:tenantb``\ 와 같은 지정은 사용하지 마십시오.
``virtual_host``\ 는 기본적으로 검색에 사용할 수 있는 필드에 포함되지 않아, 이 문자열 전체를 본문에서 찾는 검색으로 처리되므로 의도한 문서를 선택할 수 없습니다.

인스턴스를 나누는 선택지
========================

하나의 Fess를 공유하는 구성에서는 다음 사항을 나눌 수 없습니다.

- 관리 화면과 관리자: 어느 관리자든 모든 테넌트의 설정, 사용자, 문서를 조작할 수 있다
- [일반]의 설정이나 사전 등 시스템 전체의 설정
- 로그인 화면

테넌트마다 관리를 맡기고 싶거나 계약상 인덱스를 나눌 필요가 있는 경우에는, 테넌트마다 Fess를 기동하고 인덱스 이름을 나눕니다.
docker-fess의 ``compose/multi-instance``\ 는 하나의 OpenSearch에 2개의 Fess(포트 8080과 8081)를 연결하는 구성입니다.

::

    $ git clone https://github.com/codelibs/docker-fess.git
    $ cd docker-fess
    $ git checkout v15.9.0
    $ cd compose/multi-instance
    $ docker compose -f compose.yaml -f compose-fess01.yaml -f compose-fess02.yaml up -d

각 Fess의 ``FESS_JAVA_OPTS``\ 에서 문서, 서제스트, 크롤링, 설정, 사용자, 로그, 사전의 인덱스 이름(``-Dfess.config.index.document.search.index=fess01.search`` 등 8개 항목)을 인스턴스마다 바꾸고 있습니다.
설정과 사용자도 인덱스별로 나뉘므로 관리 화면, 사용자, 검색 로그도 테넌트 단위가 됩니다.
테넌트를 늘릴 때는 ``compose-fess02.yaml``\ 을 복제하고 서비스 이름, 포트, 인덱스 이름을 모두 바꿉니다.

.. warning::

   이 구성의 OpenSearch는 보안 플러그인이 비활성화된 채 포트 9200을 공개합니다.
   9200에 접근할 수 있는 사람은 모든 테넌트의 인덱스를 읽을 수 있으므로, 운영 환경에서는 포트를 닫으십시오.
