==============================================
オープンソースで実現するファイルサーバ全文検索
==============================================

はじめに
========

部門ごとにファイルサーバが増えていくと、「あの資料はどこにあるか」が誰にもわからなくなります。
Windows の検索は共有フォルダー単位でしか機能せず、サーバが複数あると横断できません。
NAS の全文検索機能も、機器をまたいでは使えません。

この問題を解決する方法のひとつが、ファイルサーバ専用の全文検索サーバを立てることです。
本ページでは、オープンソースの全文検索サーバ Fess でファイルサーバを検索対象にする場合に、導入前に確認しておきたい点をまとめます。
内容は Fess 15.9 に合わせています。

対象読者
========

- 社内のファイルサーバや NAS の検索に困っている方
- 全文検索の導入を検討していて、オープンソースで実現できるか知りたい方
- 既存のアクセス権限を壊さずに検索を導入したい方

Fess は Apache License 2.0 で公開されており、ライセンス費用なしで利用できます。

どこに置かれたファイルを検索できるか
====================================

Fess のファイルクロールは、以下のプロトコルに対応しています。
設定は管理画面の［クローラー］>［ファイルシステム］で、「パス」にクロールを開始する場所を指定します。

.. list-table:: 対応プロトコル
   :header-rows: 1
   :widths: 12 33 55

   * - プロトコル
     - パスの書式
     - 主な用途
   * - ``file``
     - ``file:/home/share/documents/``
     - Fess を動かすサーバ上のディレクトリ。マウント済みの NAS もここに含まれます
   * - ``smb``
     - ``smb://fileserver.example.com/share/``
     - Windows ファイル共有や、SMB で公開している NAS
   * - ``smb1``
     - ``smb1://fileserver.example.com/share/``
     - 旧来の SMB1 実装を使う接続。古い機器で ``smb`` がつながらない場合の予備
   * - ``ftp``
     - ``ftp://fileserver.example.com/pub/``
     - FTP サーバ
   * - ``s3``
     - ``s3://bucket-name/prefix/``
     - Amazon S3 および S3 互換のオブジェクトストレージ（\ ``fess-storage-s3`` プラグインが必要）
   * - ``gcs``
     - ``gcs://bucket-name/prefix/``
     - Google Cloud Storage（\ ``fess-storage-gcs`` プラグインが必要）

Fess 本体が扱うプロトコルは設定値 ``crawler.file.protocols`` で決まっており、15.9 の既定値は ``file,smb,smb1,ftp`` です。
``s3`` と ``gcs`` は 15.9 で本体からプラグインに分離されました。
Docker イメージには両プラグインが同梱されていますが、ZIP や RPM/DEB で導入した Fess では［システム］>［プラグイン］からインストールし、Fess を再起動してから使います。

Windows ファイル共有を検索する場合は ``smb`` を使います。
``smb`` は、Fess 側で特に設定しなければ SMB1 から SMB 3.1.1 までの範囲でサーバと接続バージョンを決めます。
``smb1`` は別の実装（旧来の jcifs）で接続するための指定で、新規に選ぶものではありません。

既存のアクセス権限をそのまま引き継ぐ
====================================

ファイルサーバに検索を導入するとき、いちばん大きな懸念は「見えてはいけない文書が検索結果に出てしまうこと」です。
人事や経理の共有フォルダーが全社員の検索結果に並んでしまえば、検索システムそのものが使えません。

Fess はこれを、ファイルサーバ側のアクセス権限を検索に持ち込むという方法で解決します。
ただし、新しく作ったクロール設定のままでは権限による出し分けは効きません。以下の仕組みと、次の「パーミッション欄の {role}guest を消す」を必ず確認してください。

仕組み
------

1. クロール時に、Fess は各ファイルの ACL（アクセス制御リスト）を読み取ります
2. 読み取りを許可されたアカウントとグループ、拒否されたアカウントとグループを、その文書の「ロール」として ``role`` フィールドに記録します
3. クロール設定の「パーミッション」欄に書いた値も、同じ ``role`` フィールドに追加されます
4. 検索時に、ログインしているユーザーが持つロールと突き合わせ、権限のある文書だけを返します

``role`` フィールドには、ユーザーは ``1``、グループは ``2`` を名前の前に付けた形で記録されます（例: ``1taro``、``2sales``\ ）。
拒否のエントリには、さらに ``D`` が前に付きます（例: ``D2contractors``\ ）。
パーミッション欄で ``{role}guest`` と書いた値は ``Rguest`` として記録されます。
管理画面で見かける ``(allow)`` と ``(deny)`` は、パーミッション欄に入力するときの書き方で、記録される値ではありません。

ACL からロールを取り出す動作は既定で有効です。

.. list-table:: 権限の引き継ぎに関する設定値（fess_config.properties）
   :header-rows: 1
   :widths: 38 14 48

   * - 設定値
     - 既定値
     - 内容
   * - ``smb.role.from.file``
     - ``true``
     - ``smb`` と ``smb1`` でクロールしたファイルの ACL からロールを取得します
   * - ``file.role.from.file``
     - ``true``
     - ``file`` でクロールしたファイルのアクセス権からロールを取得します（後述の注意を参照）
   * - ``ftp.role.from.file``
     - ``true``
     - ``ftp`` でクロールしたファイルの所有者とグループからロールを取得します
   * - ``smb.available.sid.types``
     - ``1,2,4:2,5:1``
     - ロールとして採用する SID の種類と、記録するときの種類。既定ではユーザー（1）とドメイングループ（2）をそのまま、ローカルグループ（4）をグループとして、Everyone などの組み込みの SID（5）をユーザーとして記録します

パーミッション欄の {role}guest を消す
-------------------------------------

［クローラー］>［ファイルシステム］で新規作成すると、「パーミッション」欄にはあらかじめ ``{role}guest`` が入っています。
このまま保存すると、すべての文書に ACL 由来のロールと並んで ``Rguest`` が付きます。
ログインしていない利用者には ``guest`` ロールが与えられるため、\ **ACL で制限したファイルも、未ログインの検索では全件表示されます**\ 。

ACL による出し分けを効かせるには、クロール設定の「パーミッション」欄から ``{role}guest`` を削除して保存します。
すでにクロール済みの場合も、次回のクロールで新しいパーミッションの文書として登録し直されます。

なお、ログインしたユーザーには ``guest`` ロールは付きません。
そのため ``{role}guest`` を残していても、ログインしたユーザーには ACL どおりの結果が返ります。
「動作を確認する」で示すように、必ず未ログインの状態でも確かめてください。

ログイン側の名前と一致させる
----------------------------

この仕組みが最後まで機能するには、検索する側のユーザーにも同じロールが付いている必要があります。
文書側には「このグループなら読める」と記録されているので、検索するユーザーが自分の所属グループを Fess に伝えられなければ突き合わせができません。

そのため、権限を引き継いだ検索を行うには Active Directory や LDAP との連携が前提になります。
ファイルサーバの認証に使っているディレクトリと同じものを Fess のログインにも使う、という構成です。
LDAP の設定は［システム］>［全般］で行います。
手順とロールの考え方は :doc:`guide-05` で説明しています。

突き合わせは名前の文字列で行われるため、次の点に注意してください。

- ACL から取った名前は、ドメイン名を含まないアカウント名で記録されます（\ ``EXAMPLE\taro`` なら ``1taro``\ ）
- LDAP でログインしたユーザーのグループ名は、既定では ``memberOf`` の CN から取られます。ファイルサーバ側のグループのアカウント名と CN が異なると一致しません
- Everyone などの組み込みグループは、その名前のロールとして記録されます。LDAP でログインしたユーザーには通常そのロールは付かないため、組み込みグループだけで公開しているフォルダーは誰にも表示されないことがあります。必要に応じてクロール設定を分け、パーミッション欄でロールを補ってください

逆に、全社員が同じ範囲を見てよい共有フォルダーだけを対象にするのであれば、この連携は必須ではありません。
この点が、導入範囲を決めるときの分かれ目になります。

プロトコルごとの注意
--------------------

``smb`` / ``smb1``
   クロール用のアカウントには、ファイルの中身に加えて、ファイルのアクセス権（セキュリティ情報）を読み取る権限が必要です。
   アクセス権を読み取れなかったファイルはインデックスされず、［システム情報］>［障害URL］に記録されます。

``file``
   ファイルシステムが ACL を提供していない場合（一般的な Linux のファイルシステムなど）は、所有者のユーザーとグループの 2 つだけをロールとして記録します。
   「その他」に読み取りを許していても、それはロールになりません。
   NAS を Fess のサーバにマウントして ``file`` でクロールすると、NAS 側の ACL ではなくマウントポイントで見える所有者が記録されます。
   ACL で出し分けたいファイルサーバは、マウントせずに ``smb`` で直接クロールしてください。

``ftp``
   FTP サーバが返す所有者とグループをロールとして記録します。

どのファイル形式の中身まで読めるか
==================================

Fess は Apache Tika を利用して、ファイルの中身からテキストを抽出します。
ファイル名だけでなく本文が検索対象になるため、「タイトルを思い出せない資料」も見つけられます。

主な対応形式は次のとおりです。

- MS Office（doc, xls, ppt, docx, xlsx, pptx など）
- PDF
- テキスト、HTML、XML
- リッチテキスト（rtf）
- ソースコード（js, c, h, java など）
- 圧縮ファイル（gz, tar, zip など）

網羅した一覧は `検索対象ファイル <https://fess.codelibs.org/ja/supported-files.html>`__ を参照してください。

画像 PDF やスキャン文書のように、テキストを含まないファイルは、そのままでは本文を検索できません。
Fess 15.9 では Tesseract による OCR を有効にでき、画像ファイル、Office 文書に埋め込まれた画像、テキストを含まない PDF から文字を読み取れます。
OCR は既定で無効です。
クローラーが動くホストに ``tesseract`` をインストールし、``crawler.document.ocr.enabled=true`` を設定します。
一部のページだけがスキャン画像の PDF は対象外です。
手順は `OCR（画像内の文字認識）の設定 <https://fess.codelibs.org/ja/stable/config/crawler-ocr.html>`__ を参照してください。
OCR を使うとクロールの時間が延びるため、対象フォルダーにスキャン文書がどれだけあるかを先に確認しておくことをおすすめします。

構成と規模
==========

Fess は検索インデックスの格納に OpenSearch を使います。
小規模であれば Fess と OpenSearch を同じサーバに同居させる構成で動きますが、対象ファイルが増えてきたら OpenSearch をクラスター構成にして分離できます。

規模を見積もるときは、ファイル数だけでなく次の点を確認しておくと精度が上がります。

- 対象フォルダーの合計サイズと、そのうちテキストを含むファイルの割合
- 更新頻度（毎日変わるのか、月に数回か）。クロールの実行間隔の設計に影響します
- 1 ファイルあたりのサイズ

インデックスできるファイルサイズには、既定で上限があります。
``app/WEB-INF/classes/crawler/contentlength.xml`` の既定値は HTML が 2.5MB、それ以外が 10MB で、これを超えるファイルはインデックスされず［障害URL］に記録されます。
これとは別に、クロール設定の「設定パラメーター」に ``client.maxContentLength=10485760`` のように書くと、取得するファイルのサイズ自体を制限できます（既定は制限なし）。
大きな資料が多いフォルダーでは、上限を見直すかどうかを導入前に決めておきます。
設定方法は `クローラー設定 <https://fess.codelibs.org/ja/stable/config/crawler-basic.html>`__ の「ファイルサイズの設定」を参照してください。

クロールの実行間隔にも注意が必要です。
Fess は、一定日数のあいだクロールで更新されなかった文書をインデックスから削除します。
この日数は［システム］>［全般］の「以前のドキュメントを削除」で、既定は 3 日です。
既定のジョブ「Default Crawler」は毎日実行されるので問題ありませんが、週 1 回などに減らす場合は、この日数を実行間隔より長くしてください。

ファイルサーバ検索ツールを選ぶ観点
==================================

ファイルサーバ向けの検索ツールを比較するときは、製品名を見比べる前に、次の点を満たしているかを確認すると選びやすくなります。

.. list-table:: 検索ツールを選ぶときの確認項目
   :header-rows: 1
   :widths: 30 70

   * - 確認項目
     - Fess の場合
   * - 複数のサーバや NAS を横断して検索できるか
     - クロール設定を複数登録することで、1 つの検索窓から横断して検索できます
   * - ファイルの本文まで検索できるか
     - Apache Tika で Office 文書や PDF の本文を抽出し、検索対象にします。スキャン文書は OCR を有効にすると対象になります
   * - 既存のアクセス権限を引き継げるか
     - SMB でクロールしたファイルの ACL からロールを取得し、検索結果を出し分けます。Active Directory や LDAP との連携と、クロール設定のパーミッション欄の見直しが必要です
   * - ライセンス費用がかかるか
     - Apache License 2.0 で公開されており、ライセンス費用はかかりません
   * - 手元で試せるか
     - Docker Compose で起動して、手元で検索を試せます

導入の流れ
==========

1. **まず動かす** — `簡単構築ガイド <https://fess.codelibs.org/ja/quick-start.html>`__ または :doc:`guide-02` の手順で Fess を起動します
2. **クロール設定を作る** — ［クローラー］>［ファイルシステム］で、名前とパスを登録します。ACL で出し分ける場合は、「パーミッション」欄の ``{role}guest`` を削除してから保存します
3. **認証情報を設定する** — 共有フォルダーにアクセスするためのアカウントを［クローラー］>［ファイル認証］に登録し、「ファイルクロール設定」で 2 の設定を選びます
4. **クロール用アカウントの権限を確かめる** — 対象フォルダーの中身とアクセス権を読み取れるアカウントかどうかを、ファイルサーバ側で確認します
5. **ログインを連携する** — ［システム］>［全般］で LDAP（Active Directory）を設定します
6. **クロールを実行して確認する** — ［システム］>［スケジューラ］の「Default Crawler」を開いて［今すぐ開始］をクリックし、次の「動作を確認する」で結果を確かめます

部門別の絞り込みが必要であれば、［クローラー］>［ラベル］でラベルも設定します。

複数のファイルサーバと社内 Web サイトを 1 つの検索窓から探せるようにする具体的な手順は :doc:`guide-04` で、ロールとグループによる出し分けの設計は :doc:`guide-05` で扱っています。
Namazu や Hyper Estraier など、すでに動いている全文検索を置き換える場合は、:doc:`legacy-search-migration` で、今の構成と Fess の機能の対応や、棚卸しから旧システムの撤去までの手順を説明しています。

動作を確認する
==============

クロールが終わったら、次の順で確かめます。
組み込みの ``admin`` ユーザーは ``guest`` ロールも持っているため、出し分けの確認には使わないでください。

1. ［システム情報］>［障害URL］を開き、アクセスエラーやサイズ超過で取り込めなかったファイルがないかを確認します
2. ［システム情報］>［検索］で、制限付きフォルダーのファイルを検索します。この画面ではロールによる絞り込みがかからないため、すべての文書が表示されます
3. 結果の［更新］をクリックして編集画面を開き、``role`` 欄を確認します。``1taro`` や ``2sales`` のような ACL 由来の値が入っていること、``Rguest`` が入っていないことを確かめます
4. ログアウトした状態で検索画面から同じファイルを検索し、表示されないことを確かめます
5. そのフォルダーを読めるグループに属するユーザーでログインして検索し、表示されることを確かめます
6. そのグループに属さないユーザーでログインして検索し、表示されないことを確かめます

3 で ``role`` 欄の名前が LDAP 側の名前と食い違っている場合は、「ログイン側の名前と一致させる」の各項目を見直します。

まとめ
======

- Fess はファイルサーバ（SMB、FTP、ローカル）を全文検索の対象にできるオープンソースの検索サーバです。S3 と GCS はプラグインで対応します
- SMB でクロールしたファイルは、ACL に記録されたアクセス権限が検索結果の出し分けに使われます。ACL の読み取りは既定で有効です
- クロール設定の「パーミッション」欄にある ``{role}guest`` を消さないと、未ログインの利用者には全件が表示されます
- 権限を引き継いだ検索を行うには、Active Directory や LDAP との連携と、両者の名前の一致が前提になります
- Apache Tika により Office 文書や PDF の本文まで検索対象になり、OCR を有効にするとスキャン文書も対象になります
- 小さく始めて、対象が増えたら OpenSearch をクラスター化して広げられます
