====================================
1 つの Fess を複数の組織で使い分ける
====================================

はじめに
========

グループ会社や部門ごとに検索サービスを提供したいとき、組織の数だけ Fess を構築すると、サーバーもクロール設定の管理も組織の数だけ増えます。
Fess の仮想ホスト機能を使うと、1 つの Fess を複数のホスト名で公開し、ホスト名ごとに検索対象・ラベル・検索画面を切り替えられます。

ただし、仮想ホストは「どのホスト名で来たか」で表示を出し分ける機能で、アクセス制御ではありません。
ほかの組織の文書を確実に見せないためには、ロールによる権限設定とログインを組み合わせる必要があります。

本記事では、A 社と B 社の 2 つのテナントを例に、次のことを Fess 15.9 で順に設定します。

- ［全般］の「仮想ホスト」でホスト名とテナントを対応付ける
- クロール設定とラベルに仮想ホストとパーミッションを指定し、テナントの文書を分ける
- 仮想ホスト名と同じ名前のテーマで、テナントごとに検索画面を変える
- テナントのユーザーでログインし、ほかのテナントの文書が見えないことを確かめる
- テナントの追加と削除を、正しい順序で行う

ロール・グループ・ユーザーの基本は :doc:`guide-05` で扱います。

先に押さえること：仮想ホストはアクセス制御ではない
==================================================

Fess はリクエストごとに、［全般］の「仮想ホスト」に書いた行を上から順に評価し、指定したヘッダー（通常は ``Host``）の値が一致した最初の行の仮想ホスト名（以下、キー）を使います。
キーが決まると、次の機能がそのキーで絞り込まれます。

- 検索結果：クロール設定の「仮想ホスト」にそのキーを持つ文書だけが返ります（検索 API も同じです）
- ラベル：「仮想ホスト」欄がそのキーのラベルだけが表示されます
- キーマッチ・関連コンテンツ・関連クエリー：「仮想ホスト」欄がそのキーの設定だけが使われます
- 検索画面：キーを小文字にした名前のテーマがあれば、そのテーマで表示されます

一方、どの行にも一致しないリクエストでは、この絞り込みがすべて行われません。
サーバーの IP アドレスで直接アクセスした場合や、リバースプロキシが ``Host`` ヘッダーを書き換えた場合は、仮想ホストによる絞り込みがなくなり、権限で見える範囲の全テナントの文書が検索対象になります。
［全般］のホスト名の書き間違いやポート番号の付け忘れも、エラーにはならず「一致しない」として扱われます。

そのため、テナント間で文書が見えないようにするには、次の 2 つを組み合わせます。

- 各テナントの文書のパーミッションを、そのテナントのロール（例: ``{role}tenanta_user``）だけにする
- 検索画面にはログインを必須にし、ユーザーにテナントのロールを割り当てる

この記事で作る構成
==================

.. list-table::
   :header-rows: 1
   :widths: 16 26 14 18 26

   * - テナント
     - 公開ホスト名
     - キー
     - ロール
     - クロール対象
   * - A 社
     - ``search-a.example.com``
     - ``tenanta``
     - ``tenanta_user``
     - ``https://portal-a.example.com/``
   * - B 社
     - ``search-b.example.com``
     - ``tenantb``
     - ``tenantb_user``
     - ``https://portal-b.example.com/``

キーには英数字とアンダースコア（``a-zA-Z0-9_``）だけが使えます。
それ以外の文字は保存時に取り除かれるため、``tenant-a`` と書くとキーは ``tenanta`` になり、クロール設定に ``tenant-a`` と書いても一致しません。
``admin``・``common``・``error``・``login``・``profile`` は予約されていて使えません。

クロール設定やラベルの「仮想ホスト」欄は自由入力で、キーとの照合は大文字・小文字を区別します。
テーマ名も小文字しか使えないため、キーは最初から小文字の英数字にそろえておくと間違いが起きません。

手順 1：ホスト名とキーを対応付ける
==================================

管理画面の［システム］>［全般］を開き、「仮想ホスト」に 1 行 1 件で ``ヘッダー名:ヘッダー値=キー`` を書いて更新します。

::

    Host:search-a.example.com=tenanta
    Host:search-b.example.com=tenantb

ヘッダー値は大文字・小文字を区別せずに完全一致で比較されます。
ブラウザーは標準ポート（80・443）以外でアクセスすると ``Host`` ヘッダーにポート番号を付けるため、Fess のポート 8080 に直接アクセスさせる場合は次のようにポートまで書きます。
両方の書き方を並べて書いてもかまいません。

::

    Host:search-a.example.com:8080=tenanta
    Host:search-b.example.com:8080=tenantb

設定は保存した時点で反映され、再起動は不要です。
``fess_config.properties`` の ``virtual.host.headers`` にも同じ形式で書けますが、［全般］に値があればそちらが優先されます。

リバースプロキシの背後に置く場合は、ブラウザーが送った ``Host`` ヘッダーを Fess まで届けます。
Nginx は既定では ``proxy_pass`` の宛先を ``Host`` にするため、``proxy_set_header Host $host;`` が必要です。

::

    server {
        server_name search-a.example.com search-b.example.com;
        location / {
            proxy_pass http://127.0.0.1:8080;
            proxy_set_header Host $host;
        }
    }

``Host`` を書き換える構成では、ヘッダー名に ``X-Forwarded-Host`` を指定する方法もあります（例: ``X-Forwarded-Host:search-a.example.com=tenanta``）。

.. warning::

   ［全般］の設定はコンテナ内の ``system.properties`` に保存されます。
   docker-fess の ``fess01`` はボリュームを持たないため、``docker compose down`` でコンテナを作り直すと「仮想ホスト」の値も消えます（``stop``・``start`` では残ります）。
   後の手順でアップロードするテーマもコンテナ内に置かれるため、同じく消えます。
   設定を残す方法は `Docker でのインストール (詳細) <https://fess.codelibs.org/ja/stable/install/install-docker.html>`__ を参照してください。

手順 2：テナントのロールとユーザーを作る
========================================

1. ［ユーザー］>［ロール］で、名前 ``tenanta_user`` と ``tenantb_user`` のロールを作成します。
2. ［ユーザー］>［ユーザー］で各テナントの利用者を作成し、「ロール」でそのテナントのロールを選びます。
3. ［システム］>［全般］で「ログインが必要」を有効にします。

ログインしたユーザーには ``{role}guest`` が付かず、ユーザー・グループ・ロールの権限だけで検索されます。
LDAP や SSO のグループをそのまま使う場合は、ロールの代わりに ``{group}<グループ名>`` で指定できます。
権限の仕組みと LDAP 連携は :doc:`guide-05`、SSO は :doc:`guide-15` を参照してください。

手順 3：テナントごとのラベルを作る
==================================

ラベルは、クロール時に URL が「対象とするパス」に一致した文書に付きます。
クロールより先に作っておきます。

［クローラー］>［ラベル］で［新規作成］を押し、A 社用に次のように入力します（B 社も同様に作ります）。

.. list-table::
   :header-rows: 1
   :widths: 30 70

   * - 項目
     - 値
   * - 名前
     - ``A 社ポータル``
   * - 値
     - ``tenanta_docs``\ （英数字とアンダースコアのみ）
   * - 対象とするパス
     - ``https://portal-a\.example\.com/.*``
   * - パーミッション
     - ``{role}tenanta_user``
   * - 仮想ホスト
     - ``tenanta``

新しいラベルのパーミッションには ``{role}guest`` が入っています。
ラベルは利用者がそのパーミッションのロールを持つときだけ表示されるため、``{role}guest`` のままだとログインしたテナントのユーザーにはラベルが表示されません。

「仮想ホスト」が空のラベルは、仮想ホストでアクセスしたときには表示されません。
1 つのラベルに指定できる仮想ホストは 1 つなので、複数のテナントで同じラベルを見せたい場合は、名前と値が同じラベルをテナントの数だけ作り、それぞれの「仮想ホスト」にキーを入れます。
キーマッチ・関連コンテンツ・関連クエリーも同じで、「仮想ホスト」が空の設定はテナントのホストでは使われません。

手順 4：クロール設定に仮想ホストとパーミッションを指定する
==========================================================

［クローラー］>［ウェブ］で、A 社用のクロール設定を作成します。
ファイルシステムとデータストアのクロール設定にも同じ 2 つの欄があります。

.. list-table::
   :header-rows: 1
   :widths: 30 70

   * - 項目
     - 値
   * - 名前
     - ``A 社ポータル``
   * - URL
     - ``https://portal-a.example.com/``
   * - クロール対象とするURL
     - ``https://portal-a.example.com/.*``
   * - パーミッション
     - ``{role}tenanta_user``\ （既定で入っている ``{role}guest`` は削除します）
   * - 仮想ホスト
     - ``tenanta``

``{role}guest`` を残すと、IP アドレスでのアクセスやログイン前のアクセスから、その文書が見えてしまいます。

グループ全社向けの規程集のように複数テナントに見せる文書は、1 つのクロール設定の「仮想ホスト」と「パーミッション」にそれぞれ 1 行ずつ両テナント分を書きます。

::

    仮想ホスト:
    tenanta
    tenantb

    パーミッション:
    {role}tenanta_user
    {role}tenantb_user

仮想ホストとパーミッションは、クロール時に文書へ書き込まれます。
すでにクロール済みの設定でこれらを変えた場合は、再クロールするまで既存の文書には反映されません。

設定を保存したら、詳細画面の［新しいジョブの作成］でテナント専用のジョブを作るか、［システム］>［スケジューラ］の ``Default Crawler`` を［今すぐ開始］で実行します。

手順 5：テナント専用の検索画面を用意する
========================================

Fess 15.9 の検索画面はテーマで表示されます。
``theme.yml`` の ``name`` がキーを小文字にしたものと同じテーマをインストールすると、そのキーのリクエストにはそのテーマが使われます。
デフォルトテーマに設定する必要はなく、どのキーにも一致しないアクセスにはデフォルトのテーマが使われます。

同梱の ``bootstrap`` テーマを複製して作ります。
Docker の場合は、次のようにコンテナから取り出します。

::

    $ docker cp fess01:/usr/share/fess/app/themes/bootstrap ./tenanta

1. ``tenanta/theme.yml`` の ``name`` を ``tenanta`` に、``displayName`` を ``A 社検索`` などに変えます。
2. ``assets/styles.css``\ （配色）や ``assets/logo-head.png``・``assets/logo.png``\ （ロゴ）を差し替えます。``index.html`` は変更不要です。
3. ``theme.yml`` が ZIP のルートに来るようにまとめます。

   ::

       $ cd tenanta && zip -r ../tenanta.zip .

4. ［システム］>［テーマ］の［アップロード］から ``tenanta.zip`` をアップロードします。

ログイン画面（``/login/``）は全テナント共通で、テーマでは変えられません。
同梱テーマの複製方法の詳細は `テーマ開発 <https://fess.codelibs.org/ja/stable/dev/theme-development.html>`__ を参照してください。

分離を確かめる
==============

DNS を切り替える前に、手元の ``/etc/hosts`` に ``127.0.0.1 search-a.example.com search-b.example.com`` を追加すると、ブラウザーから ``http://search-a.example.com:8080/`` のように各ホストを試せます（［全般］にはポート付きの行が必要です）。
次の 4 通りを、クロール対象にある語で検索して確認します。

.. list-table::
   :header-rows: 1
   :widths: 45 55

   * - アクセス
     - 期待する結果
   * - A 社ユーザーで ``search-a.example.com`` から
     - A 社の文書だけが出る。ラベルは「A 社ポータル」だけ。A 社のテーマで表示される
   * - A 社ユーザーで ``search-b.example.com`` から
     - 0 件（B 社の文書は権限がなく、A 社の文書は仮想ホストで除かれる）
   * - A 社ユーザーで IP アドレス（``http://<サーバー>:8080/``）から
     - A 社の文書だけが出る（仮想ホストの絞り込みはないが、権限で守られる）
   * - ログインせずにアクセス
     - ログインするまで検索できない

両テナント向けの共通の文書を作った場合は、1〜3 行目でその文書も出ます。
3 行目で B 社の文書が出る場合は、どこかのクロール設定に ``{role}guest`` が残っています。
1 行目で 0 件になる場合は、［全般］の行（ポート番号の有無）と、クロール設定の「仮想ホスト」の綴りを見比べます。

検索 API でも同じ確認ができます。
［システム］>［アクセストークン］でパーミッション ``{role}tenanta_user`` のトークンを作り、``Host`` ヘッダーを変えて呼び出します。

::

    $ curl -s -H "Authorization: Bearer <A 社のトークン>" \
        -H "Host: search-a.example.com:8080" \
        "http://localhost:8080/api/v2/search?q=fess"
    $ curl -s -H "Authorization: Bearer <A 社のトークン>" \
        -H "Host: search-b.example.com:8080" \
        "http://localhost:8080/api/v2/search?q=fess"

1 つ目は ``response.record_count`` が 1 以上、2 つ目は 0 になれば想定どおりです。
アクセストークンは仮想ホストに結び付いておらず、送信先のホスト名で仮想ホストが決まります。
トークンが見られる範囲を決めるのはトークンのパーミッションなので、テナントのシステムに渡すトークンには必ずそのテナントのロールだけを指定します。
API の使い方は :doc:`guide-11` を参照してください。

運用が始まったら、［システム情報］>［検索ログ］の［利用者・環境］タブで仮想ホストごとの検索数を確認できます。

テナントの追加と削除
====================

テナントを追加するときは、後の手順が前の手順の値を使うため、次の順に進めます。

1. ［全般］の「仮想ホスト」に行を追加する
2. ロール、ユーザー、必要ならアクセストークンを作る
3. ラベル（仮想ホストとパーミッション付き）を作る
4. クロール設定（仮想ホストとパーミッション付き）を作り、クロールする
5. テーマをアップロードする
6. 「分離を確かめる」の 4 通りを確認する
7. DNS とリバースプロキシで公開する

テナントを削除するときは、逆に利用の入口から止めます。

1. DNS とリバースプロキシからホスト名を外す
2. クロール設定と、そのために作ったジョブ（［システム］>［スケジューラ］）を削除する
3. インデックスから文書を削除する（下記）
4. アクセストークン、ユーザー、ロールを削除する
5. ラベル、キーマッチなどそのキーの設定と、テーマを削除する
6. ［全般］の「仮想ホスト」から行を削除する

クロール設定を削除しても、クロール済みの文書はインデックスに残ります。
文書は［システム情報］>［検索］で削除します。
この画面ではロールと仮想ホストの絞り込みがかからないため、全テナントの文書が対象です。
検索欄に ``label:tenantb_docs`` のようにテナントのラベルを指定して検索し、件数と結果が B 社の文書だけであることを確かめてから［このクエリですべてを削除］を押します。
Web の文書であれば、``site:portal-b.example.com`` のように URL の先頭部分で指定することもできます。

``virtual_host:tenantb`` のような指定は使わないでください。
``virtual_host`` は既定では検索で使えるフィールドに含まれず、この文字列全体を本文から探す検索として扱われるため、意図した文書を選べません。

インスタンスを分けるという選択肢
================================

1 つの Fess を共有する構成では、次の点は分けられません。

- 管理画面と管理者：どの管理者も全テナントの設定・ユーザー・文書を操作できる
- ［全般］の設定や辞書など、システム全体の設定
- ログイン画面

テナントごとに管理を任せたい、契約上インデックスを分ける必要がある、といった場合は、テナントごとに Fess を起動し、インデックス名を分けます。
docker-fess の ``compose/multi-instance`` は、1 つの OpenSearch に 2 つの Fess（ポート 8080 と 8081）をつなぐ構成です。

::

    $ git clone https://github.com/codelibs/docker-fess.git
    $ cd docker-fess
    $ git checkout v15.9.0
    $ cd compose/multi-instance
    $ docker compose -f compose.yaml -f compose-fess01.yaml -f compose-fess02.yaml up -d

各 Fess の ``FESS_JAVA_OPTS`` で、文書・サジェスト・クロール・設定・ユーザー・ログ・辞書のインデックス名（``-Dfess.config.index.document.search.index=fess01.search`` など 8 項目）をインスタンスごとに変えています。
設定とユーザーもインデックスごとに分かれるため、管理画面・ユーザー・検索ログもテナント単位になります。
テナントを増やすときは ``compose-fess02.yaml`` を複製し、サービス名・ポート・インデックス名をすべて変えます。

.. warning::

   この構成の OpenSearch はセキュリティプラグインが無効のまま、ポート 9200 を公開します。
   9200 に届く人は全テナントのインデックスを読めるため、本番ではポートを閉じてください。
