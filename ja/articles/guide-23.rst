==========================================
全社展開の進め方：段階ごとのチェックリスト
==========================================

はじめに
========

Fess の試用がうまくいき、全社に広げることになったとき、迷うのは機能そのものより順番です。
設定によっては、後の段階に回すと手戻りが大きくなります。
たとえば、認証情報を登録した後で暗号鍵を変えると保存済みの値を復号できなくなり、文書のパーミッションを後から変えると再クロールが必要になります。

本記事は、Fess 15.9 を全社に展開する順序を段階ごとに示します。
各段階について、設定すること、確かめること、次の段階へ進んでよいかを判断する指標を挙げます。
指標には、管理画面の［システム情報］>［検索ログ］の分析レポートを使います。
個々の機能の手順は説明せず、その機能を扱う記事にリンクします。

構成要素と担当する記事
======================

全社展開で扱う構成要素と、それぞれを詳しく扱う記事は次のとおりです。

- Fess 本体：検索画面、管理画面、API、スケジューラを提供します。全体像は :doc:`guide-01`、メモリと台数の拡張は :doc:`guide-14`
- OpenSearch：文書のインデックスに加え、クロール設定、ユーザー、ジョブログ、検索ログも保存します。分離とクラスター化は :doc:`guide-14`、スナップショットは :doc:`guide-10`
- クローラーなどの子プロセス：クロール、サジェスト生成、サムネイル生成、チャンク処理は、ジョブごとに Fess 本体とは別の JVM で動きます。ヒープの設定は :doc:`guide-14`
- プラグイン：データストア（``fess-ds-*``）、SSO（``fess-sso-*``）、LLM と埋め込み（``fess-llm-*``）、MCP やマルチモーダル検索（``fess-webapp-*``）など。Fess と同じマイナーバージョン（15.9.x）を入れ、導入と削除の後は Fess を再起動します。作り方は :doc:`guide-17`
- LLM と埋め込みモデル（任意）：AI 検索モードとセマンティック検索で使う外部のサービス、または Ollama などのサーバーです。設定は :doc:`guide-18`、:doc:`guide-19`

OpenSearch に保存されないものは、Fess のサーバーごとに管理します。
［システム］>［全般］の設定（``system.properties``）、``fess_config.properties``\ （暗号鍵 ``app.cipher.key`` を含む）、導入したプラグインの 3 つです。
これらの控え方は :doc:`guide-10`、コードでの管理は :doc:`guide-16` を参照してください。

段階の一覧
==========

.. list-table::
   :header-rows: 1
   :widths: 22 40 38

   * - 段階
     - 目的
     - 次へ進む目安
   * - 1. 試用
     - 少数の利用者に検索させ、何が探されるかを知る
     - 人気の検索語とゼロヒット語を、記録として残せた
   * - 2. 最初の情報源を公開
     - 権限付きで 1 つ目の情報源を公開し、運用の基本を整える
     - 利用者数とクリック率の基準値を記録した
   * - 3. SSO とログイン
     - 社内の ID でログインさせ、グループで結果を出し分ける
     - 「ロール・グループ別の検索数」に IdP のグループが現れる
   * - 4. 情報源を増やす
     - SaaS、クラウドストレージ、データベースを加える
     - 文書不足が原因だったゼロヒット語が消える
   * - 5. 品質改善のサイクル
     - 検索ログから問題の語を見つけて直す
     - 前の期間と比べて、直した指標が悪化していない
   * - 6. 規模の拡張と自動化
     - 文書と利用者の増加に備え、環境を再現できるようにする
     - ［パフォーマンス］タブの応答時間が、利用者が増えても拡張前より悪化していない
   * - 7. AI 機能
     - AI 検索モード、セマンティック検索、MCP を加える
     - ［AIチャット］タブでリクエストが記録され、エラー率が導入直後より上がっていない

どの段階も、前の段階の設定を前提にしています。
特に段階 2 と段階 3 は、後から変えると再クロールが必要になる設定を含むため、順番を入れ替えないでください。

段階 1：試用
============

検証用の Fess を立て、一部の部署に使ってもらいます。
この段階の目的は、利用者が何を探しているかを検索ログとして集めることです。

**設定すること**

- :doc:`guide-02` の手順で、docker-fess の ``v15.9.0`` タグの Compose ファイルを使って起動し、初回ログインでパスワードを変更する
- 対象を 1 つのサイトや 1 つのフォルダーに絞ってクロール設定を作る
- ［システム］>［全般］の「検索ログ」と「ユーザーログ」が有効であることを確かめる（どちらも既定で有効）。「ユーザーログ」が無効だと利用者数が集計されない

**確かめること**

- ［システム情報］>［ジョブログ］でクロールのジョブが「OK」になり、［システム情報］>［クロール情報］で登録件数が 0 でない
- 件数が少なければ［システム情報］>［障害URL］を見る（:doc:`guide-02`）

**次へ進む目安**

- ［検索ログ］の［概要］タブで、試用期間の検索数、利用者数、人気の検索語、ゼロヒット語が表示される
- ゼロヒット語をクリックし、［ログ］タブで実際の検索を確かめたうえで、:doc:`guide-08` の表に沿って原因を「言い換え」「誘導」「文書がない」に分ける
- 「文書がない」に分けた語は、段階 2 と段階 4 で加える情報源の候補にする。表の CSV をダウンロードして残しておく

段階 2：最初の情報源を公開
==========================

全社の利用者が使う情報源を 1 つ選び、権限付きで公開します。
同時に、本番運用に必要な監視とバックアップを整えます。

**設定すること**

- 暗号鍵 ``app.cipher.key`` を、ウェブ認証・ファイル認証やデータストアのパラメーターに認証情報を登録する前に決める。登録後に変えると保存済みの値を復号できない（:doc:`guide-16`、:doc:`guide-10`）
- Web サイトと共有フォルダーのクロール設定、ファイル認証、ラベルを作る（:doc:`guide-04`）。ファイルサーバーの ACL を検索結果に反映する場合は :doc:`file-server-search`
- パーミッションの設計を決める（:doc:`guide-05`）。新しいクロール設定とラベルにはパーミッション ``{role}guest`` が入っており、そのままではログインしていない利用者にも見える。部署で見せ分ける文書は、この値を消してから ``{group}`` などを書く
- ``{group}`` に書くグループ名は、段階 3 で IdP から届く名前に合わせておく。後で名前を変えると、パーミッションの書き換えと再クロールが必要になる
- 週 1 回などのジョブで回すクロール設定がある場合は、［全般］の「以前のドキュメントを削除」（既定 3 日）をクロールの間隔より長くする（:doc:`guide-04`）
- 監視、通知、バックアップを設定する（:doc:`guide-10`）。``/api/v2/health`` を外部の監視ツールから呼び、［全般］の「通知メール」か「Slack Webhook URL」を設定し、［システム情報］>［バックアップ］のファイルを管理 API で毎日取得する
- Docker の場合、［全般］の設定は ``fess01`` コンテナ内の ``system.properties`` に保存され、``down`` でコンテナを作り直すと消える。バックアップに含めるか、``FESS_JAVA_OPTS`` で渡す（:doc:`guide-02`、:doc:`guide-16`）
- 必要に応じて、社内ポータルに検索窓を置く（:doc:`guide-03`）

**確かめること**

- 部署の異なる利用者でログインし、見える文書が変わる。部署向けの文書に記録された権限に、初期値の guest ロールが残っていない（確かめ方は :doc:`guide-05`）
- ``/api/v2/health`` が 200 を返し、［全般］の［テストメールの送信］でメールが届く
- バックアップのスクリプトを一度手で実行し、取得したファイルが空でない（:doc:`guide-10`）

**次へ進む目安**

［検索ログ］では、この段階の監視やバックアップの状態はわかりません。
それらは上の「確かめること」で判断します。
検索ログでは、公開後の利用状況の基準値を取ります。

- ［概要］タブで、公開後の期間の検索数、利用者数、ゼロヒット率、クリック率を確かめ、CSV で残す。以降の段階では、この値と「前の期間と比較」で比べる
- ［クリック］タブの「クリック数の多いURL」に、公開した情報源の URL が並ぶ
- ［全般］の「以前の検索ログを削除」に日数を指定すると、それより古いログは比較に使えない（既定の ``-1`` は削除しない）。保存期間を決めておく

段階 3：SSO とログイン
======================

社内の ID 基盤（IdP）でログインさせ、IdP のグループで検索結果を出し分けます。

ここでいう SSO は、Fess 15.9 ではプラグインで提供される 4 つの方式です。
Entra ID は ``fess-sso-entraid``、OpenID Connect は ``fess-sso-oidc``\ （「SSOタイプ」は ``oic``）、SAML は ``fess-sso-saml``、SPNEGO は ``fess-sso-spnego`` を使います。
Docker イメージには 4 つとも入っていますが、``-slim`` のイメージには入っていません。
ZIP・RPM・DEB 版では、［システム］>［プラグイン］か ``bin/fess-setup`` で入れます。

LDAP は SSO ではありません。
［全般］の LDAP 設定は、Fess のログイン画面で入力された ID とパスワードを Active Directory などで確かめ、所属グループを取得する機能です（:doc:`guide-05`）。
SPNEGO は、グループの取得にこの LDAP 設定を使います。

**設定すること**

- プラグインを入れて Fess を再起動し、［全般］の「SSOタイプ」と IdP の情報を設定する。IdP に登録する戻り先は ``https://<Fessのホスト>/sso/``\ （:doc:`guide-15`）
- TLS を終端するリバースプロキシの背後に置く場合は、外部のスキームとポートを Fess に伝える（:doc:`guide-15`）
- ログインしていない利用者に検索させない場合は、［全般］の「ログインが必要」を有効にする

「ログインが必要」は、検索画面以外にも効きます。

- ``/api/v2/`` の検索 API は、ログインセッションか有効なアクセストークンがない呼び出しに 401 を返す。業務システムからの呼び出しにはトークンを用意する（:doc:`guide-11`）
- MCP の既定の ``mcp.auth.mode=none`` では、``/mcp`` が AI エージェントからの呼び出しを HTTP 403 で拒否する。使う場合はアクセストークンで認証する設定に変える（:doc:`guide-20`）

**確かめること**

- ``/sso/`` を開いて IdP 経由でログインでき、部署ごとに見える文書が段階 2 の設計どおりに変わる（:doc:`guide-15`）
- Fess を複数台で動かしている場合は、ロードバランサーでスティッキーセッションを有効にしている。15.9 のログインセッションは各 Fess のメモリにある

**次へ進む目安**

- ［検索ログ］の［利用者・環境］タブの「ロール・グループ別の検索数」に、IdP から届いたグループの行が ``{group}<グループ名>`` の形で並ぶ
- グループの行が現れない場合は、利用者がログインせずに検索している（``{role}guest`` の行に計上される）か、グループが Fess に届いていない
- ［概要］タブの利用者数が、段階 2 の基準値から大きく減っていない。ログインの導入で利用をやめた部署がないかを、「ロール・グループ別の検索数」の利用者数の列で確かめる

段階 4：情報源を増やす
======================

Web サイトとファイルサーバー以外の情報源を、データストアのプラグインで加えます。
すべての情報源で共通の手順（プラグインの導入、パラメーターとスクリプト、パーミッション、ジョブ、結果の確かめ方）は :doc:`datastore-basics` にまとめてあります。
最初にこれを読んでください。

**設定すること**

- 情報源ごとにプラグインを入れて再起動する

  - Git、Confluence・Jira、Slack：``fess-ds-git``、``fess-ds-atlassian``、``fess-ds-slack``\ （:doc:`guide-06`）
  - Google Drive、SharePoint・OneDrive、Box：``fess-ds-gsuite``、``fess-ds-microsoft365``、``fess-ds-box``\ （:doc:`guide-07`）
  - データベース、CSV、Salesforce：``fess-ds-db``、``fess-ds-csv``、``fess-ds-salesforce``\ （:doc:`guide-12`）
  - 対応するプラグインがない情報源は、自分でプラグインを作る（:doc:`guide-17`）

- データストアの設定にも ``{role}guest`` が入っている。情報源の権限を引き継ぐか、段階 2 の ``{group}`` で書くかを、設定ごとに決める
- 設定ごとに［新しいジョブの作成］でジョブを分け、API のレート制限や認証情報の期限を情報源ごとに扱えるようにする
- 情報源ごとにラベルを付け、検索画面で絞り込めるようにする。データストアの設定にはラベルの欄がないため、スクリプトかラベルの「対象とするパス」で付ける（:doc:`datastore-basics`）

**確かめること**

- データストアのジョブは、コネクタでエラーが起きても「OK」で終わることがある。［クロール情報］の「インデックスのサイズ (データストア)」、［障害URL］、``fess-crawler.log`` を合わせて確かめる（:doc:`datastore-basics`）
- 権限を引き継いだ情報源では、権限の異なる利用者で検索して見える文書が変わる

**次へ進む目安**

- 段階 1 と段階 2 で「文書がない」に分けたゼロヒット語が、加えた情報源の後の期間で［検索語］タブのゼロヒット語から消える
- ［クリック］タブの「クリック数の多いURL」に、加えた情報源の文書が現れる。現れない情報源は、検索されていないか、結果の上位に出ていない。後者は段階 5 で扱う

段階 5：品質改善のサイクル
==========================

情報源がそろったら、検索ログを定期的に見て、問題のある語を直します。
直し方の選び方と反映の手順は :doc:`guide-08` が扱います。

**設定すること**

- ゼロヒット語には同義語か関連クエリー、下位に埋もれる文書にはキーマッチかドキュメントブーストを使う（:doc:`guide-08`）。同義語の辞書を変えたら、［システム情報］>［メンテナンス］でドキュメントインデックスをリロードする
- 日本語・英語・中国語が混在する文書で取りこぼしがある場合は、言語ごとのフィールドと辞書を確かめる（:doc:`guide-09`）
- 組み込みのレポートにない集計（検索語ごとに開かれた URL、ロール別のゼロヒット語、長期間の月ごとの推移など）が必要になったら、OpenSearch Dashboards を使う（:doc:`guide-22`）
- 辞書やキーマッチの設定をコードで管理する場合は :doc:`guide-16`

**確かめること**

- 直した語で検索画面から検索し、狙った文書がヒットする、または上位に出る
- キーマッチは、詳細画面の「URL」欄に対象の文書が表示される（:doc:`guide-08`）

**次へ進む目安**

この段階に終わりはなく、繰り返し行います。
1 回の改善の効果は次のように確かめます。

- 期間を「カスタム」にして変更した日の翌日から取り、「前の期間と比較」を有効にする
- ゼロヒット語を直した場合は［概要］タブのゼロヒット率と［検索語］タブのゼロヒット語、順位を直した場合は［検索語］タブの平均クリック順位と［クリック］タブのクリック順位の分布を見る
- 直した語が一覧から消え、全体の指標が前の期間より悪化していなければ、その変更は残す

段階 6：規模の拡張と自動化
==========================

文書や利用者が増えたら、足りなくなったものを確かめてから拡張します。
あわせて、同じ環境を作り直せるようにします。

**設定すること**

- 何が足りないかを、症状ごとに確かめる（:doc:`guide-14`）。``fess-crawler.log`` の OutOfMemoryError はクローラーの JVM（``jvm.crawler.options``）の不足で、Fess 本体のヒープ（``FESS_HEAP_SIZE``）を増やしても直らない
- OpenSearch を別のサーバーに分ける、3 台のクラスターにする、Fess を複数台にする、の順に検討する（:doc:`guide-14`）
- Fess を複数台にする場合は、クロールを 1 台に任せる。``scheduler.target.name`` と［システム］>［スケジューラ］の「対象」の両方を設定する（:doc:`guide-14`）
- 複数台では、``app.cipher.key``、``fess_config.properties``、［全般］の設定、プラグインをすべての台でそろえる
- Docker イメージのタグとプラグインの版を固定し、設定を fessctl と管理 API で適用できるようにする（:doc:`guide-16`）
- 1 つの Fess を複数の組織で使い分ける場合は、仮想ホストとロールを組み合わせる。仮想ホストだけではアクセス制御にならない（:doc:`guide-13`）

**確かめること**

- 拡張の前後で、``/api/admin/stats`` のヒープ使用率と、［システム情報］>［ジョブログ］のクロールの所要時間を比べる（:doc:`guide-10`）
- 複数台では、どの台から開いても同じ検索結果になり、クロールは担当の台だけで動く。ほかの台で［今すぐ開始］をクリックしても実行されない（:doc:`guide-14`）
- 作り直した環境に、バックアップから設定を戻せる（:doc:`guide-10`）

**次へ進む目安**

- ［検索ログ］の［パフォーマンス］タブで、応答時間の中央値・p95・p99 が拡張前より下がっている、または利用者が増えても上がっていない
- 「応答の遅い検索語」に並ぶ語を検索し、特定の語だけが遅いのか、全体が遅いのかを分ける

なお、ログインセッションを OpenSearch に保存して複数台で共有する機能は、15.10 以降で使えます。
15.9 では、前述のスティッキーセッションで運用します。

段階 7：AI 機能
===============

AI 機能は、機能ごとに必要な準備が異なります。
目的に合うものから加えます。

**AI 検索モード（RAG）**

- 利用者の質問に、社内文書を根拠にして LLM が答える機能です（:doc:`guide-19`）
- ベクトル検索は必要ありません。根拠の文書は通常の検索で集めるため、段階 2〜3 のパーミッションがそのまま効き、利用者が見られない文書は回答に使われません
- ``fess_config.properties`` の ``rag.chat.enabled=true``\ （既定は ``false``、管理画面に項目なし）、``fess-llm-*`` プラグイン、［全般］の「LLMプロバイダー」の 3 つが必要です
- 使える利用者は［全般］の「チャット権限」で絞れます

**セマンティック検索とマルチモーダル検索**

- セマンティック検索は、キーワードが一致しなくても意味の近い文書を探します（:doc:`guide-18`）。埋め込みのプロバイダーを ``content_chunker.embedding.name`` で選びます。既定の ``opensearch`` は OpenSearch の ML Commons のモデルを使い、``ollama``・``openai``・``gemini``・``bedrock`` は対応する ``fess-llm-*`` プラグインが必要です
- 既存の環境で有効にする場合は、インデックスを作り直してから全文書のベクトルを作ります。OpenAI などの従量課金のモデルでは、最初の処理で全文書分の料金が発生します
- マルチモーダル検索は、プラグイン ``fess-webapp-multimodal`` と CLIP のサーバーを使い、テキストで画像を探します（:doc:`guide-21`）
- この 2 つは、1 つの Fess では同時に使えません。両方が必要な場合は Fess を分けて構築します

**MCP**

- AI エージェントから Fess を検索させる機能です（:doc:`guide-20`）。プラグイン ``fess-webapp-mcp`` を入れると ``/mcp`` が使えます
- 既定の ``mcp.auth.mode=none`` では、``/mcp`` に届く人は誰でもゲストとして検索できます。社内に公開する前に、アクセストークンなどで認証する設定に変えます

**確かめること**

- AI 検索モード：検索画面の［AI 検索］で質問し、回答と出典が表示される。権限の異なる利用者で、見られない文書が出典に現れない（:doc:`guide-19`）
- セマンティック検索・マルチモーダル検索：文書にベクトルが書き込まれ、検索 API の応答でベクトル検索が使われている（:doc:`guide-18`、:doc:`guide-21`）
- MCP：認証の設定を変えた後、トークンのない呼び出しが拒否される（:doc:`guide-20`）

**次へ進む目安**

- AI 検索モードは、［検索ログ］の［AIチャット］タブで、リクエスト数、利用者数、エラー率、平均応答時間を見る。トークン数は LLM プラグインが報告した場合だけ記録され、質問と回答の内容は記録されない
- セマンティック検索は、導入した日の翌日からの期間で「前の期間と比較」を有効にし、ゼロヒット率、クリック率、［パフォーマンス］タブの応答時間を比べる
- MCP とマルチモーダル検索には、［検索ログ］に専用の指標がない。上の「確かめること」と、利用部署からの報告で判断する
